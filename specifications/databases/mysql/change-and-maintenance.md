# MySQL 变更与数据维护规范

本规范约束需求上线和专项维护中的 MySQL 结构与存量数据变更，说明如何新增或修改结构、处理旧数据，以及下线、归档和清理。适用于 MySQL 8.4、阿里云 RDS 和 Go 应用，基础配置遵守 [MySQL 基线](baseline.md)，目标库表设计遵守 [库表设计规范](schema-design.md)。

更新日期：2026-11-02。

## 1. 操作分类与共同要求

### 1.1 先确定需要做哪些操作

| 操作类型 | 处理什么 | 例子 | 对应章节 |
| --- | --- | --- | --- |
| 新增结构 | 增加原来没有的库、表、字段或索引 | 为帖子增加摘要字段，为订单列表增加索引 | 第 2 章 |
| 修改结构 | 调整已有定义，或改变数据的组织方式 | 扩大字段长度、重命名字段、把用户扩展信息拆到独立表 | 第 3 章 |
| 处理存量数据 | 初始化、补齐、纠正或搬迁已有数据 | 回填旧帖摘要，修复错误的会员到期时间 | 第 4 章 |
| 下线结构 | 停止使用并最终删除库、表、字段或索引 | 下线旧字段，删除不再使用的索引 | 第 5 章 |
| 归档与清理 | 转移低频历史数据，或永久删除符合条件的数据 | 归档超过保留期的已删除帖子及其点赞关系 | 第 6 章 |

一个需求可以包含多类操作。例如，“新增帖子摘要”包含新增字段、上线摘要写入逻辑和回填旧数据；“拆分用户扩展信息”包含新建表、搬迁数据、切换读写和下线旧字段。必须列全这些操作，分别满足对应要求。

### 1.2 所有操作都要遵守的要求

1. **先说明目的和范围。** 记录需求、负责人、目标环境、RDS 实例、业务库、库表或数据范围，以及完成后的预期结果。同一实例上的其他业务库也要纳入负载影响评估。
2. **通过版本管理和评审。** 结构使用增量 SQL 迁移，按业务库归属放入应用的 `database/` 目录，同一业务库的结构迁移由统一入口按依赖顺序执行。数据任务的代码、SQL 和参数同样纳入版本管理，记录验证方法和失败后的处理办法。已执行的脚本不再修改，后续修正追加新脚本。
3. **先测试，再执行。** 在与目标环境一致的 MySQL 8.4 配置下验证，生产变更还须核对实际 RDS 内核和数据规模。测试应覆盖执行耗时、新旧代码兼容及中途失败，不能只在空表上验证语法。
4. **维护入口同样遵守基线。** 应用、迁移工具、脚本和管理客户端都使用规定的 TLS、字符集和 UTC 会话。结构与 Go 模型同步维护；生产应用启动时禁止执行 `AutoMigrate`。
5. **明确执行和停止条件。** 记录执行人、执行时间、脚本版本、实际结果及异常。耗时较长的操作须提前确定批次大小、执行速度、资源与复制延迟的停止阈值；达到阈值时暂停或中止，不能持续冲击业务。
6. **先准备恢复办法。** 修改或删除已有数据、收缩结构前，确认可用的备份、必要的变更前数据和恢复步骤。代码回退、结构恢复和数据修复分别说明，不能只写“失败时回滚”。

普通维护只操作归属库。确需同时修改多个业务库的数据时，遵守库表设计规范中的受控跨库本地事务要求；不能为了维护方便给普通服务长期开放跨库写权限。

### 1.3 结构变更与数据修改分开执行

建表、改字段、建索引等属于 DDL；插入、更新、删除记录属于数据修改。常规 DDL 会隐式提交，不能把 DDL 与业务数据修改包进一个事务后，期待一起回滚。MySQL 的原子 DDL 也不表示多条迁移语句能整体回滚。参见 [隐式提交说明](https://dev.mysql.com/doc/refman/8.4/en/implicit-commit.html)和 [原子 DDL 说明](https://dev.mysql.com/doc/refman/8.4/en/atomic-ddl.html)。

**先理解执行方式**

- `ALGORITHM` 决定如何改表：`INSTANT` 主要修改表定义；`INPLACE` 可能构建索引或重建表；`COPY` 复制数据到新表再替换，通常会限制业务写入。具体支持哪种，取决于本次修改和现有表结构。
- `LOCK` 约束主要执行期间是否允许业务读写，例如 `LOCK=NONE` 允许同时读写。但改表仍可能短暂取得保护表定义的“元数据锁”，因此仍有等待或阻塞的可能。参见 [MySQL 执行方式与锁说明](https://dev.mysql.com/doc/refman/8.4/en/innodb-online-ddl-performance.html)。
- RDS“非阻塞 DDL”和 DMS“无锁结构变更”是减少业务阻塞的能力，仍有支持范围和资源开销。使用前须核对当前实例、本次操作是否支持，以及相关功能是否启用。参见 [RDS 非阻塞 DDL](https://help.aliyun.com/zh/rds/apsaradb-rds-for-mysql/non-blocking-ddl)和 [DMS 支持范围](https://help.aliyun.com/zh/dms/lock-free-structure-change/)。

**执行前检查**

1. **方式是否支持。** 在目标 RDS 环境验证本次操作支持的 `ALGORITHM` 和适用的 `LOCK` 要求；不支持预定方式时停止，重新评审。参见 [Online DDL 支持范围](https://dev.mysql.com/doc/refman/8.4/en/innodb-online-ddl-operations.html)。
2. **是否会一直等锁。** 检查未结束的长事务和锁等待。长事务可能让改表等锁，并连带挡住后续请求；明确最多等多久，超过上限结束本次尝试。
3. **资源是否够用。** 检查剩余空间、CPU、磁盘 I/O 和复制延迟，明确业务变慢或资源异常时的中止条件。允许业务继续读写，不代表建索引等操作不会抢占资源。

例如，给大表加索引前，先验证可用 `ALGORITHM=INPLACE, LOCK=NONE`。不支持就停止，不能现场改成会长时间阻止写入的方式；即使支持，也须检查长事务和资源余量，避免等锁或建索引拖慢业务。

**执行异常处理**

- 多条语句执行到一半失败，或连接中断、结果不明确时，先核对实际结构、已提交数据及执行记录，再决定从哪里继续；不能直接整份重跑。

## 2. 新增结构

### 2.1 新增业务库或业务表

- 新需求先判断能否放入现有服务与业务库。只有新增独立服务时，才按服务边界新增业务库；不能每个功能都建一个库。
- 新表先明确一行代表什么、数据归谁维护、与其他对象是什么关系，以及业务唯一性。类型、雪花主键、注释和索引等遵守库表设计规范。
- 建库、建表必须同时声明 `utf8mb4` 与 `utf8mb4_0900_bin`；新表使用 InnoDB。禁止物理外键、`CHECK` 约束和 `AUTO_INCREMENT`，业务校验由应用维护。
- 先创建结构并核对实际定义，再发布依赖该结构的应用。应用使用只读实例或代理时，也须确认其读写路径已能访问新结构。
- 新表是否需要历史数据必须单独说明。建表成功不等于旧数据已经搬迁，也不等于业务可以立即切换。

例如，新增用户扩展信息表时，应先确定是否每位用户最多一条扩展记录，再设计 `user_id` 的唯一性；扩展表保留自己的雪花 `id`。

### 2.2 新增字段

新增前检查现有 SQL：`INSERT` 必须显式列出列名，查询结果不能依赖 `SELECT *` 的列数或列顺序，避免加列后破坏旧代码。

默认按以下顺序处理：

1. **先增加兼容字段。** 尚无值的旧数据使用 SQL `NULL`，Go 模型使用对应可空类型。只有统一默认值对旧数据和新增数据都有明确业务含义，且兼容现有写入时，才可直接采用该默认值。
2. **让新写入维护该字段。** 发布兼容代码，覆盖应用、后台任务、脚本和导入入口。过渡期间读取方式必须明确，不能直接假定所有记录都有新值。
3. **处理旧数据。** 全部旧写入入口及其在途事务退出后，按第 4 章回填并核对。滚动发布期间可能产生错误或过期值，不能只检查 `NULL`。
4. **切换读取。** 完整验证后再让业务依赖新字段；涉及只读实例时，须等待所需结构和回填结果同步到对应读取端。
5. **最后收紧定义。** 确需改为 `NOT NULL` 时，在回填完成、新写入稳定且回退版本兼容后执行。不得用无业务含义的 `0`、空字符串或虚构时间填满字段。

例如，为帖子增加 `content_preview`，约定保存正文前 120 个字符：先增加可空字段；新代码在同一事务中维护正文和摘要，过渡期间继续从正文生成展示摘要；旧写入入口退出后分批核对所有旧帖，修正摘要；确认无差异后切换读取。该字段是派生数据，后续修改正文时仍须同步维护。

### 2.3 新增索引或唯一约束

- 普通索引必须对应实际查询，按库表设计规范第 3 章验证读取收益、写入成本和执行计划。
- 新增唯一约束前，按目标字段、比较规则和业务范围检查重复数据，先处理冲突，再建唯一索引。不能任意删除重复行，也不能依赖迁移工具丢弃冲突数据。
- 默认在最终重复检查至唯一索引生效期间，暂停相关的新增和改键操作，防止检查后又写入重复数据。无法接受该窗口时，必须先验证所有写入口的业务键串行化方案；仅在插入前查询一次不能防止并发重复。
- 不新增物理外键或数据库取值、状态 `CHECK` 约束。关联、合法取值和状态流转由应用统一校验。

完成后核对实际索引定义，并复测相关查询和写入；执行成功但定义或业务结果不符合预期，不能验收。

## 3. 修改结构

### 3.1 修改字段属性

| 修改内容 | 执行要求 |
| --- | --- |
| 类型、数值范围或小数精度 | 检查旧值是否越界、精度是否丢失，以及 Go 类型和计算逻辑是否兼容；不能依赖隐式截断或四舍五入处理数据 |
| 字符串长度 | 扩大长度时核对执行方式、索引限制和应用校验；缩短前先找出超长数据，按业务规则处理，禁止直接截掉内容 |
| 可空性 | 改为非空前先解决所有 `NULL`，并确保全部写入口都能提供值；改为可空时同步修改 Go 映射和业务判断 |
| 默认值 | 明确省略字段时的含义，检查应用是否依赖原默认值；修改默认值不会替业务回填已有记录 |
| 字符集或比较规则 | 检查实际字符列、查询比较和业务唯一性。只修改库表默认值不会转换已有字符列；转换前处理不兼容数据和冲突 |
| 注释 | 同步业务含义、单位、状态编码和时间语义；业务含义已改变时，按新增字段及数据迁移处理 |

使用 `MODIFY COLUMN` 等语句时，完整声明目标类型、精度、可空性、默认值和注释，避免漏写原有属性。参见 [ALTER TABLE 字段修改说明](https://dev.mysql.com/doc/refman/8.4/en/alter-table.html)。

每次变更都要验证现有数据可转换、新写入合法、读取结果正确，并核对 `SHOW CREATE TABLE` 与 Go 模型。

### 3.2 重命名字段或表

默认采用“新增目标结构 → 兼容读写 → 迁移并核对 → 切换 → 下线旧结构”的方式。直接改名会让仍在运行的旧 SQL 失效，不能在新旧版本并存时直接执行。

- 盘点应用、后台任务、管理脚本、导入导出和报表中对旧名称的引用。
- 明确过渡期间哪个字段或表是数据来源。需要同时写入新旧结构时，通过受控事务保证一致，不能遗漏任一入口，也不通过触发器维持业务逻辑。
- 切换后保留旧结构至回退窗口结束。允许回退的代码版本必须继续维护已被业务使用的新数据，不能回到只写旧结构的版本。
- 确认引用全部退出后，按第 5 章删除旧结构。

### 3.3 拆表、合表或调整关联关系

先按库表设计规范第 1.4 节重新确定记录粒度、业务身份和关系数量，再设计迁移，不能直接按列把数据搬过去。

1. 明确每条旧记录对应哪些新记录，哪些标识保留、哪些新对象需要独立雪花 ID，并保存必要的映射。保留的业务对象不重新生成 ID。
2. 覆盖当前状态、历史记录、软删除数据及关联数据，明确每类数据的去向和保留规则。
3. 明确搬迁期间的写入方式，避免复制完成后旧表又出现未同步的更新。同一 RDS 内确需跨库写入时，使用受控本地事务。
4. 完成数据搬迁后，核对映射完整性、业务唯一性和关联关系，再切换读写。
5. 旧结构按第 5 章下线；搬迁任务按第 4 章分批执行并记录进度。

例如，把用户扩展信息拆为一对一附属表，需要为附属记录生成独立 `id`、保留 `user_id` 并约束其唯一性，还要明确未填写扩展信息的用户是否需要记录。

### 3.4 调整已有索引或业务唯一性

- 调整普通索引的字段、顺序或类型时，先建立并验证目标索引，再按第 5 章退出旧索引，避免中途失去关键查询所需的索引。
- 调整业务唯一性时，先明确新规则，验证旧数据与全部应用入口，再按 2.3 控制写入并建立目标约束；目标约束生效、旧规则依赖退出后，才能移除旧约束和开放新规则下的写入。

例如，订单号从全局唯一改为租户内唯一，需要先补齐并校验 `tenant_id`、改造订单定位条件，再建立 `(tenant_id, order_no)` 唯一约束；旧全局唯一约束退出后，才允许不同租户使用相同订单号。

## 4. 处理存量数据

### 4.1 区分数据处理的目的

| 操作 | 含义与要求 | 例子 |
| --- | --- | --- |
| 初始化 | 为新功能建立必要的初始数据，明确数据来源和业务唯一键，重复执行不能重复创建 | 初始化服务端维护的业务配置；不能因新建会员表就为所有用户开通会员 |
| 回填 | 为旧记录补上新需求需要的数据，必须有可靠来源或计算规则；无法推导时保留未知状态或进入待处理清单 | 从帖子正文生成摘要 |
| 纠错 | 修正已经写错的数据，明确错误范围、正确依据和修改条件，保存变更前值及处理结果 | 按错误批次修复会员到期时间，避免覆盖后续正常续费 |
| 搬迁 | 把已有业务事实放到目标结构，保持必要的标识、时间和关联，不重新执行原业务动作 | 把用户扩展信息搬入新表，不重新注册用户 |

### 4.2 分批、可重试地处理

- **先圈定范围。** 执行前用查询确认目标记录、数量、关键值和访问条件，写清租户及软删除数据是否包含在内。大批量修改必须按明确范围分批执行。
- **按稳定键分批。** 默认单任务顺序执行，批次大小和速度通过测试确定。使用主键或“时间 + ID”游标，不用不断增大的 `OFFSET`。雪花 ID 不代表提交顺序，不能把一次 `MAX(id)` 当作完整时间快照；并发新增、延迟提交必须由新写入逻辑或补扫覆盖。
- **防止覆盖新数据。** 按当前行值直接计算，或使用版本条件、行锁保护。不得先读出旧值，隔很久后再无条件写回。维护点赞计数等数据时，继续遵守业务已有的加锁顺序和一致性要求。
- **重复执行不重复生效。** 根据目标状态、任务明细或幂等标识判断是否已处理，不能在重试时再次累加金额、延长会员或重复建立关联。
- **提交后再推进进度。** 检查执行错误与影响行数，区分幂等未改动和条件冲突；每批显式提交，失败回滚本批。确认提交成功后才记录完成位置；提交结果不明确时先核对。任务恢复可能重复处理上一批，因此仍须满足幂等要求。
- **保留核对依据。** 记录任务版本、参数、进度、成功及失败数量。纠错和删除还须保存可用于恢复的原值或归档位置。时间字段须说明保留历史时间还是记录本次修改时间，不能让 ORM 自动时间维护悄悄覆盖原值。

例如，回填帖子摘要时，可以在更新语句中从当前 `content` 计算目标值；校验摘要时须同时识别 `NULL` 和内容不符，不能只用 `<>` 比较而漏掉 `NULL`。

### 4.3 历史库表整改

历史数据不符合现行规范时，先查清含义与影响，再按本章整改。未完成项必须记录负责人和处理计划，不能因应用暂时兼容就视为合规。

| 历史问题 | 整改要求 |
| --- | --- |
| 时间含义不清或混用时区 | 按来源和批次确认真实语义，再转换为 UTC；不能只改会话时区或给整列统一减 8 小时。时间类型迁移还须验证真实时刻未改变 |
| 使用自增或其他历史主键 | 新写入接入统一雪花组件，先核对与已有 ID 的冲突风险；保留仍有效的旧 ID 和关联。确需换 ID 时，必须有完整映射及关联迁移方案 |
| 存在物理外键或 `CHECK` 约束 | 先让所有写入口接管对应关联与业务校验，验证后再移除数据库约束；主键、业务唯一性和非空要求继续保留 |
| 存在重复数据或错误关联 | 按业务确定保留、合并或更正方式，并处理相关引用；不能仅按最小 ID 保留一行就删除其他记录 |

订单、权益变更历史等业务事实的纠错，应采用明确的业务补偿或独立更正记录，保留原始依据；不能覆盖历史后重新触发支付、会员发放等动作。

### 4.4 完成标准

数据任务必须同时验证：目标范围已完整覆盖、目标值符合规则、关联及业务唯一性仍成立，并且正常读写没有被破坏。仅比较总行数或抽查几条记录不构成完整验收；大数据量可以分段核对，但须覆盖约定的全部范围。

验证以主库真实结果为准，使用只读实例的业务还须确认数据已同步。全部目标记录处理并验证通过后，才能标记完成；剩余异常须列入未完成清单，不能标记全量完成。

## 5. 下线与删除结构

### 5.1 先停止依赖

- 找齐依赖旧库、表、字段和索引的代码、任务、脚本及报表，完成替换或停用，清理 ORM 映射和显式索引提示。
- 停止写旧字段前，检查省略该字段是否仍能正常插入。例如旧字段为无默认值的 `NOT NULL` 时，不能先从 Go 模型删除字段就发布，须先安排兼容处理。
- 明确保留期限、观测范围、回退截止时间和仍允许回退的应用版本，覆盖低频任务，不能只观察几次接口请求。

### 5.2 再删除结构

- 删除库、表或字段必须与首次切换分开执行，在依赖退出、观测完成且回退窗口结束后，通过独立迁移删除。
- 删除前确认需要保留的数据已经按第 6 章处理，恢复方法经过验证。应用回退时不得自动执行删列、删表等反向脚本。
- 删除普通索引可先设为不可见，按库表设计规范第 3 章观察影响；唯一索引仍承担业务约束，不能因为查询不用它就删除。
- 完成后核对实际结构、应用模型和关键读写，更新已执行记录。不得用 `IF EXISTS` 等写法掩盖目标结构与预期不一致的问题。

## 6. 归档、清理与恢复

### 6.1 先确定数据的保留方式

| 方式 | 用途与边界 |
| --- | --- |
| 软删除 | 在业务查询中隐藏记录，保留原数据用于恢复；不减少数据量，也不等于归档 |
| 归档 | 把低频历史数据保存到明确的归档位置，保留查询或恢复能力；归档成功后，才可按规则清理源数据 |
| 物理清理 | 永久移除源记录；须确认保留期限、业务依赖和恢复要求均已满足 |
| 备份 | 用于故障或误操作恢复，受备份周期和可恢复范围限制；不能替代业务归档 |

每类数据分别规定保留期限、可恢复期限、清理条件、关联数据处理和归档数据自身的保留策略。不能仅凭 `created_at` 很早或 `deleted_at` 非空就判定可以永久删除。

关注、点赞等当前关系仍按库表设计规范处理：用户取消时物理删除；有历史留存需求时单独保存行为历史，不能统一改为软删除。

### 6.2 先归档验证，再清理源数据

1. **确定清单。** 固定本批目标及其关联数据范围，记录归档版本、来源和去向。需要归档的关联必须一起考虑，不能只复制主体。
2. **控制并发变化。** 归档与清理期间须阻止目标数据被修改或恢复，或者使用已验证的版本核对机制；发生变化时重新归档并验证，不能继续按旧副本删除。
3. **写入并验证归档。** 保留原 ID、时间、状态和必要关联，记录数量及内容核对结果，验证能够读取和恢复。归档副本不重新生成业务 ID，归档位置须有相应访问控制。
4. **分批清理。** 按已验证清单删除，删除前复核状态或版本。先处理依赖记录，再处理主体；数据量大时分批提交，在全部批次结束前持续阻止产生新关联或恢复主体。
5. **核对并留存结果。** 记录已清理、待重试和异常项，检查关联、计数及查询结果。归档失败或验证未通过时，不得删除源数据。

归档目的地在数据库外时，不应在数据库事务中长时间等待上传；通过任务状态、版本和删除前复核，保证清理的正是已成功归档的那一版数据。

### 6.3 帖子与点赞关系的清理例子

`post` 软删除后，`post_like` 和点赞计数仍保留，支持恢复。只有业务明确帖子超过保留期限后不再恢复，才可进入归档清理。

清理时先把该帖子纳入受控清理任务，并让应用阻止恢复和新关联；按既定帖子锁规则复核状态。归档帖子及当时仍存在的点赞关系，验证后分批删除点赞关系，每批事务同步扣减计数。最后核对关系清空、计数归零且没有其他依赖记录，再删除帖子。

清理任务跨多个事务时，阻止恢复的状态必须持续有效；仅检查 `deleted_at IS NOT NULL` 不足以阻止另一个入口恢复帖子。此前已取消、已经物理删除的点赞不属于归档关系，恢复时也不得重新建立。

### 6.4 误操作恢复与空间回收

- 生产环境须确认 RDS 存在成功的数据备份，并按恢复要求启用日志备份、核对实际可恢复时间范围及恢复耗时。仅开启 Binlog 不能证明任意时刻均可恢复。参见 [RDS 时间点恢复保护](https://help.aliyun.com/zh/rds/apsaradb-rds-for-mysql/any-point-in-time-recovery-protection)。
- 误操作后默认先恢复到隔离的新实例，确认受影响记录，再生成受控修复方案。历史恢复点之后的合法写入必须保留，不能直接用旧表覆盖线上。参见 [RDS 全量恢复说明](https://help.aliyun.com/zh/rds/apsaradb-rds-for-mysql/restore-full-data-of-an-apsaradb-rds-for-mysql-instance)。
- 从归档或备份恢复数据时，核对当前主键、业务唯一性、关联和后续业务变化；恢复记录不等于重新执行购买、续费、关注等业务动作。
- 删除记录后，数据文件不保证立即缩小。需要碎片整理或重建表时，作为独立结构变更安排窗口、资源和验证，不能在清理任务结束后自动对整表执行优化。参见 [RDS 空间碎片回收说明](https://help.aliyun.com/zh/rds/apsaradb-rds-for-mysql/use-the-automatic-fragment-reclamation-feature-for-an-apsaradb-rds-for-mysql-instance)。

# MySQL 库表设计规范

## 1. 库表组织、业务建模、命名与注释

### 1.1 应用与 RDS 实例

本节中的“应用”指一套完整业务系统，可以包含订单服务、用户服务等多个业务服务。同一个服务的多个运行副本仍属于同一服务。

同一环境中，一个应用使用一个独立的 RDS MySQL 实例，应用下所有业务库都部署在该实例上。开发、测试、生产环境分别按此关系组织。

RDS 实例按应用分配，业务库按服务划分。服务之间共用该应用的 RDS 实例，为同实例内的跨库本地事务提供条件。

### 1.2 服务与业务库及业务表

一个业务服务对应一个业务库，业务库下按业务需要建立多张业务表。服务负责其所属库表的业务含义、约束和结构维护；这项归属不等于禁止经过明确约束的跨库事务写入。

例如，一个会员商城应用包含订单服务和用户服务：

| 应用 | RDS 实例 | 业务服务 | 业务库 | 业务表示例 |
| --- | --- | --- | --- | --- |
| 会员商城 | 实例 A | 订单服务 | `order_service` | `sales_order`、`sales_order_item` |
| 会员商城 | 实例 A | 用户服务 | `user_service` | `user_profile`、`user_address` |

订单服务的多个副本和所属后台任务共同使用 `order_service` 库，用户服务的多个副本和所属后台任务共同使用 `user_service` 库，不按进程或副本数量另建业务库。

### 1.3 普通访问与受控跨库本地事务

普通业务操作默认访问本服务所属的业务库。需要原子修改多个业务库的流程，可以通过受控的本地事务访问多个库；未明确约定的跨库写入禁止执行。

“受控”必须同时满足以下要求：

| 要求 | 具体约束 |
| --- | --- |
| 明确业务范围 | 说明哪个业务流程需要跨库、涉及哪些表和字段，以及必须一起成功的操作 |
| 统一执行入口 | 由一个明确的事务处理模块执行，避免各模块自行拼接跨库写入；该模块可以放在现有服务内 |
| 限制访问权限 | 使用专用账号或连接配置，只授予该流程需要的库表、字段和操作权限，普通连接保持自身业务库的权限范围 |
| 使用一个本地事务 | 涉及的表必须位于同一 RDS 主实例且均为 InnoDB，所有查询、加锁和更新都使用同一个连接上的同一个 `sql.Tx` |
| 协调结构变更 | 参与流程的字段或业务语义发生变化时，维护方必须同步检查事务处理模块 |

数据库权限能够限制访问范围，但无法识别代码当前是否正在执行指定业务流程，因此还必须在代码中集中事务入口，限制跨库连接的使用范围。

**购买会员的支付回调示例**：要求 `order_service.membership_order` 的订单支付状态与 `user_service.user_membership` 的当前会员权益一起更新。

本例将用户资料和会员权益分表保存，假定每个用户最多一份当前会员权益，会员表对 `user_id` 设置唯一约束。创建或变更会员权益的入口统一先锁定所属用户，再处理会员记录，避免首次创建与其他会员操作互相竞争。对象拆分和关系建模的通用要求见 1.4。

| 项目 | 本流程约定 |
| --- | --- |
| 执行入口 | 订单服务内的会员购买回调处理模块 |
| 跨库访问范围 | 查询订单和用户所需数据，更新订单支付状态及会员权益相关字段 |
| 一致性要求 | 订单状态更新与会员权益更新在一个事务中提交或回滚 |
| 普通访问边界 | 该流程的授权不扩展为订单服务其他模块任意修改用户数据的权限 |

回调校验通过后，按以下顺序处理：

1. 从该 RDS 主实例连接开启一个 `sql.Tx`，查询并锁定 `order_service.membership_order` 中的目标订单，检查本次支付是否已经处理。
2. 在同一个事务中先查询并锁定 `user_service.user_profile` 中的目标用户，确认用户存在；再按 `user_id` 读取并锁定已有的 `user_service.user_membership` 记录，按统一会员规则计算权益。
3. 仍使用同一个 `sql.Tx` 保存计算后的会员权益：已有记录则更新，不存在则先分配雪花 `id` 并新建；然后更新订单支付状态。任一检查或写入失败，程序必须回滚整个事务。
4. 两项更新都完成后统一提交，只有 `Commit` 明确成功后才确认回调处理成功。

例如，会员更新成功后，订单状态更新失败，则程序回滚事务，会员更新也不会被提交。两项更新及提交都成功后，订单支付状态和会员权益一起生效。

重复回调必须进行幂等检查；只有确认本次支付对应的订单状态与会员权益已一起处理完成，才可直接按成功处理。提交时报错可能意味着结果尚不确定，应通过幂等检查、重试或结果核对确认，不能仅凭报错认定事务已回滚。

这里的本地事务由回调处理模块直接操作两个库完成；调用用户服务的 HTTP 接口，或分别从两个连接池各开一个事务，都不会自动加入这个 `sql.Tx`。库名限定与连接级事务说明参见 [MySQL 对象限定名](https://dev.mysql.com/doc/refman/8.4/en/identifier-qualifiers.html)和 [Go 事务说明](https://go.dev/doc/database/execute-transactions)。

### 1.4 业务对象与关系建模

本节规定业务对象、对象之间的关系以及业务变化如何映射为表和记录。设计顺序统一为：确定每行记录的含义，判断对象是否需要拆分，再确定关联方式和业务唯一性，最后设计字段与索引。

#### 1.4.1 先确定记录粒度和业务身份

每张表在设计字段之前，必须在设计说明中明确以下内容：

| 项目 | 必须明确的内容 |
| --- | --- |
| 记录含义 | 每行表示一个对象、一条关系，还是一次发生的业务事件 |
| 业务范围 | 记录在哪个服务、租户或其他业务范围内成立 |
| 记录粒度 | 同一对象或对象组合保存一条当前记录，还是允许按业务事件、版本或有效期间保存多条记录 |
| 重复判断 | 哪些业务条件相同就应视为重复，哪些变化属于更新原记录，哪些变化应创建新记录 |
| 存在与消失 | 没有记录代表什么，何时创建、解除、删除或归档，以及是否需要保留历史 |

同一张表中的记录必须保持相同的粒度和字段含义。不能让部分行表示当前对象，另一些行表示该对象的某次操作，也不能只靠给表增加技术主键来回避业务重复的判断。

记录的技术标识与业务身份分别设计。所有业务表按 2.3 使用独立生成的雪花 `id`，附属表、关联表和历史表也不例外；哪些业务内容不能重复，按本节确定的记录粒度落实到 2.4 的业务唯一约束。

#### 1.4.2 按业务职责决定对象的拆分与合并

采用 DDD 时，实体表示需要持续识别的业务对象，值对象表示按属性值表达含义的数据，聚合用于确定共同维护业务约束的对象范围。这些概念帮助划分业务职责，不与数据库表建立固定的一一对应关系。

一个聚合可以使用多张表；拆表也不自动要求拆成多个聚合或服务。单值的值对象默认展开为所属表的字段；其集合需要逐项查询、约束或修改时，再设计附属表。适合整体读写、没有独立关系或生命周期的附属集合，仍按 2.1 判断是否使用 JSON。不能根据 Go 结构体或 GORM 模型的数量直接决定表的数量。参见 [DDD 实体与聚合](https://learn.microsoft.com/en-us/dotnet/architecture/microservices/microservice-ddd-cqrs-patterns/microservice-domain-model)和 [值对象](https://martinfowler.com/bliki/ValueObject.html)。

拆分与合并按以下规则判断：

| 数据特征 | 落表规则 | 例子 |
| --- | --- | --- |
| 同一对象的固定单值属性，业务职责、生命周期和维护方式一致 | 默认保存在同一张表；不能仅因代码中分成多个结构体就拆表 | 用户名称、头像地址都属于用户基本资料，默认一起存入 `user_profile` |
| 业务职责独立，并具有自身操作流程、生命周期或保留规则的对象或附属信息 | 默认独立建表，明确与主体的关联和记录数量限制 | 用户资料存入 `user_profile`；有开通、续费、到期流程的会员权益存入 `user_membership`，通过 `user_id` 关联。每用户最多一份当前权益时，对 `user_id` 设置唯一约束 |
| 同一主体下可能存在多条同类条目，且需要分别查询、约束或修改 | 使用子表或关联表，每个条目保存为一行；不通过不断增加编号字段、拼接 ID 字符串或保存关系 ID 数组代替关系建模 | 一笔订单包含多项商品时，每项在 `sales_order_item` 中保存一行，通过 `order_id` 关联 `sales_order` |
| 仅因字段较大、访问频率不同而考虑拆分 | 必须有实际访问或存储依据，并评估拆分后的关联访问和维护成本，不能仅按字段数量决定 | 文章列表只读标题、摘要，而正文很大；实测拆分有收益时，可将正文放入 `article_content`，通过唯一的 `article_id` 关联 `article` |
| 多种对象只因展示在同一页面、由同一接口返回而考虑合并 | 分别按业务职责建模，通过查询组织返回结果；展示方式不决定存储边界 | 订单详情同时展示订单和用户资料时，`sales_order` 与 `user_profile` 仍分别维护，数据各由所属服务提供，再由应用组装返回 |

一对一关系也需要按上述规则判断是否拆表。并非每组可选字段都需要扩展表，也不能因为两个对象一对一，就认定它们具有相同的业务职责和生命周期。

一个字段默认由它实际描述的对象维护。若字段描述的是关系、某次发生的事件或业务快照，应放入对应的记录中；同一对象的数据不应被无理由地复制到多张关系表中。数据拆分与减少重复维护的原则参见 [关系数据规范化说明](https://learn.microsoft.com/en-us/previous-versions/troubleshoot/microsoft-365/microsoft-365-apps/access/database-normalization-description)。

#### 1.4.3 根据关系基数确定关联方式和唯一性

关系落表前，必须写清参与对象、各自角色、关联是否必选，以及各方允许关联多少条记录。对于三元及更多元关系，还须说明：固定其余参与方后，某一方允许出现一个还是多个对象。

关系的元数按业务含义判断，不能只数表中有几个 `_id`。技术主键、操作者、租户范围等列，不因名称包含 `id` 就自动成为新的关系参与方。

| 关系 | 落表规则 | 例子 |
| --- | --- | --- |
| 一对一（含一对零或一） | 需要拆表时，在保存关联的一方设置关联列，并对限定该对应关系的业务键建立唯一约束；关联是否可空按业务可选性确定。附属表保留自己的雪花 `id`，不以主体 ID 兼作自身主键 | 每个用户最多一份当前会员权益：`user_membership` 保留独立雪花 `id`，用非空 `user_id` 关联 `user_profile`，并设 `UNIQUE(user_id)`；用户可以没有会员记录 |
| 一对多 | 默认在“多”的一方保存“一”的对象标识。若同一个业务对象允许同时归属多个主体，应重新按多对多关系判断，不能复制同一对象来伪装成多个独立对象 | 一笔订单有多条明细：`sales_order_item` 每行保留自己的 `id`，用非空 `order_id` 关联 `sales_order`；多条明细可以具有相同的 `order_id` |
| 多对多 | 使用独立关联表，每行表达一条完整关系。只有业务规定同一范围内的对象组合最多存在一条记录时，才对该组合设置唯一约束 | 用户可有多个角色，角色也可授予多个用户：`user_role(id, user_id, role_id)` 每行保存一条当前绑定关系，设置 `UNIQUE(user_id, role_id)` 防止重复绑定 |
| 三元及更多元 | 默认用一条记录保存各参与方共同构成的关系事实。唯一键由记录粒度和各方数量限制共同确定，可以包含全部参与方，也可能只需其中一部分，不能机械拼接所有关联 ID | 假设角色定义跨项目共用，`project_user_role(id, project_id, user_id, role_id)` 表示用户在某项目担任某角色。每用户在同一项目可有多个角色时，设 `UNIQUE(project_id, user_id, role_id)`；只能有一个角色时，设 `UNIQUE(project_id, user_id)` |

以上关联列都是普通列，物理外键仍按 2.4 禁止使用。关系的存在性、归属和变化由应用维护。

每项业务唯一性要求都必须得到唯一约束保障。已有约束无法保障其他字段组合的唯一性时，分别设置相应约束；已被更小字段组合的唯一性覆盖时，不重复建立。对全部参与列建立一个联合唯一键，不能代替更小范围的唯一要求；其他业务数量限制仍由应用按 2.4 维护。

唯一约束只能限制对应业务键不重复。关联列 `NOT NULL` 只限制本条记录必须填写关联标识，不能证明目标对象存在；唯一约束也不能保证每个主体都已经创建了附属记录。业务要求“必须有一条”时，由应用在创建和删除流程中保证。

关系本身的属性保存在关系记录中，参与对象自身的属性由对象表维护。属于某次建立、变更或解除操作的信息，应按 1.4.4 判断是否需要单独记录历史，不能只因操作涉及这条关系就覆盖原有历史。

多元关系只有在拆分后仍能准确还原全部原始组合，并且保留原来的唯一性和业务规则时，才可以拆成若干低元关系。不得仅为减少关联列而拆成两两关系，导致查询拼出原本不存在的组合，或丢失原有组合。参见 [关系基数与参与方](https://opendsa-server.cs.vt.edu/ODSA/Books/Database/html/ERDRelationships.html)和 [二元与三元关系的区别](https://opendsa-server.cs.vt.edu/ODSA/Books/Database/html/ERDTernaryExample.html)。

同类对象之间的关系也遵守相同规则，关联列必须区分各方角色。业务要求树形结构时，还应由应用保证单一父节点、禁止形成环等规则，不能仅增加一个父节点标识就认定已经形成合法的树。

**仅表达当前存在与否的关系**

点赞、关注、角色绑定等仅表达当前关系是否存在的表，统一不使用软删除。记录存在表示关系尚未解除；解除时物理删除，重新建立时生成新的雪花 `id`，并记录本次建立时间。不得通过 `deleted_at`、`is_deleted` 等标记在当前关系表中保留已解除记录。

具有审批流程、有效期间或其他独立生命周期的业务记录，按其业务对象建模，不套用上述当前关系的存储规则。需要追溯关系的建立和解除过程时，另设事件或历史表；关系变化与要求保留的历史记录在同一事务中写入。

帖子点赞采用以下固定规则，`post_like` 只保存用户尚未取消的点赞，不设置软删除字段，并以 `UNIQUE(post_id, user_id)` 防止重复点赞：

| 操作 | 数据处理 |
| --- | --- |
| 点赞 | 在 `post_like` 新建关系记录，使用独立雪花 `id` |
| 取消点赞 | 物理删除对应的 `post_like` 记录；实际删除成功后才调整相关计数 |
| 再次点赞 | 新建关系记录，生成新的 `id` 和 `created_at`，不恢复或复用已删除记录 |
| 软删除帖子 | 设置 `post.deleted_at`，保留原点赞关系；普通帖子列表和点赞列表都过滤已删除帖子 |
| 恢复帖子 | 解除帖子的删除标记，仅让仍然存在的点赞关系重新可见，不重建用户已取消的点赞 |

点赞、取消点赞、删帖和恢复入口必须在事务中统一先锁定对应帖子，再检查业务状态并执行写入。帖子处于删除状态时不接受新的点赞和取消点赞操作，保留原关系供恢复使用。

同一次点赞请求的重试仍按 2.3、2.4 复用原请求身份和已分配 ID，只有用户重新发起的点赞操作才创建新记录。组合唯一键只防止当前关系重复，不能代替请求幂等；旧请求在取消点赞后重放，不得被当作新的点赞。计数维护遵守 1.4.5。

#### 1.4.4 分别设计当前状态、历史记录和业务快照

下列记录表达的时间含义不同，必须先确定用途，再设计唯一键和更新方式：

| 记录用途 | 记录粒度与维护规则 | 例子 |
| --- | --- | --- |
| 当前状态或当前关系 | 同一业务键默认保留一条当前记录；状态变化更新原记录，仅表达存在与否的当前关系在解除时按 1.4.3 物理删除 | `user_membership` 每用户至多一份当前权益记录，对 `user_id` 设置唯一约束；续费时更新该行的 `expired_at`，不为每次续费另建一条当前记录 |
| 事件或变更历史 | 每次业务发生或变化形成独立记录，同一对象组合可以多次出现；需要防止重复处理时，按事件身份设置幂等唯一键，不能只对参与对象组合唯一 | `membership_change_record` 每次续费追加一行，`user_id` 可以重复。本例一次续费事件对应一条记录，对 `(event_source, event_no)` 设置唯一约束，防止同一事件重复写入 |
| 按有效期间保存的版本 | 每行表示一个业务有效期间，明确起止边界、是否允许重叠，以及如何确定当前有效记录；对起止时间设置唯一约束不能自动防止期间重叠 | 假定每商品每币种只有一套价格，`product_price_version` 每行保存一段 UTC 有效期间的价格，采用 `[effective_at, expired_at)`（起含止不含）。变更入口统一在同一事务中先锁定商品，再检查并写入价格版本，保证起点早于终点、同币种期间不重叠 |
| 业务快照 | 保存指定业务时刻的数据及必要上下文，明确快照生成时机和来源，不随来源对象的当前值变化而覆盖 | 订单确认时，`sales_order_item` 保存当时的 `product_name_snapshot` 和约定单价 `unit_price`；商品之后改名或调价，不改写这些订单字段 |

当前状态和逐次变化默认分别存表。采用同表多版本等其他方案时，必须说明如何查询当前记录、保留历史以及保证相应唯一性，不能让两种粒度共用一套含义不清的重复判断规则。

历史记录和快照默认不随当前对象变化而改写；确需纠错时，必须保留修改依据和处理记录。历史是否保留、保留多久以及何时归档，应在设计说明中明确。

仅表达当前存在与否的关系，其解除与重新建立按 1.4.3 执行；需要保留的操作历史单独保存。其他采用软删除的业务表，仍不得将可空删除时间或任意时间戳追加到唯一键中，作为历史保留或唯一键复用的通用解决方案，相关约束继续按 2.4 执行。

#### 1.4.5 冗余数据的维护要求

冗余数据是可以从已有数据查询或计算得到、为了提高读取效率而额外保存的一份数据。常见用途是减少重复统计、减少关联查询，或提前汇总报表数据。

例如，帖子点赞关系已保存在 `post_like` 中，可以据此统计点赞数；如果再在帖子表 `post` 中保存 `like_count`，这个计数就是冗余数据。它方便读取，但点赞关系变化时，也需要维护计数。

增加冗余数据前，必须说明它服务于哪些查询、预期改善什么问题，并在设计说明中明确以下四项。

**1. 来源：明确数据从哪里来、以谁为准**

必须记录来源库表和字段、使用的业务范围和筛选条件，以及复制或计算规则。出现差异时，以明确的来源数据为准，不能让副本与来源各自修改同一个业务事实。

例如，`post.like_count` 按 `post_id` 统计 `post_like` 中保留的点赞关系，用户取消点赞时已按 1.4.3 物理删除关系记录。帖子软删除不视为用户取消点赞，该帖计数保留用于恢复；计数与关系记录不符时，以关系记录为准。

**2. 更新：明确触发操作和维护入口**

必须列出会改变冗余值的业务操作，并指定统一维护入口。应用请求、后台任务、脚本和导入等写入方式，都应执行相同的维护规则。

例如，点赞关系实际新增时计数加一，实际解除时减一；重复点赞或重复取消不能再次调整计数。并发增减应使用 `like_count = like_count + 1` 这样的原子更新，避免多个请求读取同一旧值后互相覆盖。

对可能重复或乱序的更新任务，还必须明确去重和新旧数据的判断方式，防止重复计算或旧值覆盖新值。

**3. 时效：明确必须同时生效，还是允许延迟**

每项冗余数据必须选择并说明相应要求：

- **必须同时生效**：来源数据和冗余数据在同一个事务中提交或回滚；跨库时遵守 1.3 的受控本地事务要求。
- **允许延迟更新**：明确最长允许延迟、更新任务如何保留和执行，以及失败后的重试方式。来源写入成功后，即使进程退出，也应能找出未完成的更新并继续处理；重试不得重复计数或覆盖较新的值。

例如，要求点赞关系与展示计数一起生效时，两者在同一事务中维护。允许计数短暂滞后时，必须约定延迟上限和补更新流程，不能只在来源提交后临时发起一次更新就认为处理完成。

**4. 修复：明确怎样发现差异并恢复正确结果**

必须规定核对周期或触发条件、修复入口和维护方，并说明按哪些来源数据核对、怎样补偿或重新计算。修复后应再次核对结果。

例如，实际有效点赞关系有 99 条，而 `post.like_count` 为 100，应按同一统计口径重新计算并修正计数。

修复流程必须说明如何处理重算期间发生的新增、修改和删除。重新计算后写回冗余值时，应与正常更新协调，避免用旧的统计结果覆盖并发更新后的计数。

### 1.5 命名规则

库名、表名和字段名必须表达清晰的业务含义，并在建表语句、业务 SQL、Go 代码和 ORM 映射中保持一致。

**通用要求**

- 统一使用小写英文字母、数字和下划线，以英文字母开头，以字母或数字结尾。
- 多个单词通过单个下划线连接，采用 `snake_case`。
- 使用完整、明确的英文业务词，避免拼音、生僻缩写和无意义编号。`id`、`ip`、`url` 等通用缩写可以使用。
- 同一业务概念必须使用本节“业务概念用词表”约定的词汇；集合、计量数量与统计结果的字段命名，还必须遵守“集合与统计语义命名表”。例如账户使用 `account`，账户标识使用 `account_id`，禁止改用 `acc_id`、`accountid`。
- 避免使用 MySQL 保留字，不通过添加反引号规避不合适的命名。
- 库名、表名和字段名均不得超过 64 个字符。

其中，大小写及命名风格属于公司约定；64 个字符是 MySQL 的标识符长度限制。参见[标识符长度说明](https://dev.mysql.com/doc/refman/8.4/en/identifier-length.html)和[保留字说明](https://dev.mysql.com/doc/refman/8.4/en/keywords.html)。

**单数、数量与集合命名**

1. 库名、表名、字段名中的可数业务实体名称统一使用单数，禁止自行采用复数形式。例如使用 `user_profile`、`user_address`、`user_role`，不使用 `user_profiles`、`user_addresses`、`user_roles`。表内保存多条记录或关联多个对象，不改变这一约定。
2. 集合、计量数量与统计结果必须按下文“集合与统计语义命名表”选择对应形式。例如使用 `order_count`、`user_id_list`、`permission_id_set`，不使用 `orders_count`、`user_ids` 等复数形式表达数量或集合。集合是否适合存入单个字段、采用何种类型，在字段设计时另行判断。
3. 标准单位和固定业务术语保留约定写法。例如 `file_size_bytes` 中的 `bytes` 表示字节单位，`timeout_ms` 中的 `ms` 表示毫秒，`sales_order` 中的 `sales` 是销售业务修饰词，不机械改为单数或删除末尾的 `s`。

`status`、`business`、`address` 本身不是复数，不能仅凭名称是否以 `s` 结尾判断是否违规。命名评审应结合业务含义和本节用词约定检查。

**集合与统计语义命名表**

本表规定集合结构、计量数量与统计结果的字段命名形式，使用的业务词汇仍须遵守“业务概念用词表”。这些形式属于公司命名约定，相关统计计算可参见 [MySQL 聚合函数说明](https://dev.mysql.com/doc/refman/8.4/en/aggregate-functions.html)。

| 语义 | 命名形式 | 示例 | 使用要求 |
| --- | --- | --- | --- |
| 列表 | `<对象>_list` | `user_id_list` | 保留元素顺序，是否允许重复须明确 |
| 集合 | `<对象>_set` | `permission_id_set` | 元素唯一，业务不依赖顺序 |
| 键值映射 | `<键对象>_<值含义>_map` | `region_price_map` | 明确键和值分别表示什么，键必须唯一 |
| 对象个数 | `<对象>_count` | `order_count` | 明确统计的对象和范围 |
| 去重对象个数 | `<对象>_distinct_count` | `user_distinct_count` | 明确按哪个标识去重 |
| 业务计量数量 | `<业务>_quantity` | `purchase_quantity` | 明确单位，如件、千克；与对象个数区分 |
| 统计求和 | `<指标>_sum` | `payment_amount_sum` | 表示指定范围内某指标的求和结果 |
| 算术平均值 | `<指标>_avg` | `payment_amount_avg` | 明确样本范围和计算口径 |
| 数值最小值 | `<指标>_min` | `payment_amount_min` | 表示统计范围内的最小值 |
| 数值最大值 | `<指标>_max` | `payment_amount_max` | 表示统计范围内的最大值 |
| 占比 | `<业务含义>_ratio` | `payment_success_ratio` | 明确分子、分母；占比统一使用 `0～1` |
| 单位时间频率 | `<事件>_rate_per_<时间单位>` | `request_rate_per_second` | 表示单位时间内的发生次数；仍须说明统计窗口 |
| 百分位值 | `<指标>_p<百分位点>` | `response_duration_p95_ms` | 表示第 95 百分位等统计结果，须明确样本范围和计算方法 |

配套要求：

1. 对象或指标名称仍使用单数，并保留必要信息。保存用户 ID 列表时使用 `user_id_list`，不使用含义模糊的 `user_list`。
2. 统计语义放在指标之后，单位放在最后。例如 `response_duration_avg_ms`、`file_size_max_bytes`。
3. 不得随意替换约定词。例如统一使用 `count`、`avg`、`map`，不混用 `cnt`、`average`、`dict`。
4. 字段注释必须说明统计口径，包括统计范围、时间窗口、去重依据，以及无样本、分母为零时的处理方式。`rate_per_second` 表达每秒的时间基准，不能代替统计窗口，例如“最近一分钟内的请求数折算为每秒请求数”。
5. 集合命名不决定存储方案。`_set` 不会自动保证去重，也不表示必须使用 MySQL `SET` 类型；是否保存集合、如何存储以及如何保证集合特性，必须在字段设计中明确。

以下边界继续适用：

- `sum` 专门表达统计求和。单笔订单的 `payable_amount`、`total_amount` 等业务金额名称，不需要因为涉及加法就机械改成 `_sum`。
- 事件时间继续遵守 `_at` 规则，例如 `first_paid_at`、`last_paid_at`，不套用 `paid_at_min`、`paid_at_max`。
- 本表的 `ratio` 行约定的是占比。其他数学比值如有独立业务含义，应另外定义，不能直接套用占比的 `0～1` 范围。

新增集合或统计语义时，必须补充本表的命名形式、示例和使用要求，并随库表设计一起评审。

**业务库命名**

业务库名称对应所属服务，统一采用 `<服务英文名称>_service`。

| 所属服务 | 推荐库名 | 避免的库名 |
| --- | --- | --- |
| 订单服务 | `order_service` | `order`、`OrderDB` |
| 用户服务 | `user_service` | `UserDB`、`yonghu` |
| 支付服务 | `payment_service` | `pay1`、`db_data` |

**业务表命名**

- 表名按每行代表的业务实体或关系使用单数名词或名词短语，遵守本节单数约定及业务概念用词表。
- 明细表、关联表必须体现所属主体或关联双方。
- 表名直接表达业务含义；需要区分业务域时，可以使用有业务含义的前缀。
- 不统一添加 `t_`、`tb_`、`tbl_` 等仅表示“这是表”的前缀。
- ORM 自动生成的名称必须符合本规范。使用 GORM 时应启用 `SingularTable: true`，关闭表名自动复数化，例如 `UserProfile` 对应 `user_profile`，而不是默认的 `user_profiles`。该配置不会重命名已有表，仍须核对实际映射的表名，参见 [GORM 命名配置](https://gorm.io/docs/gorm_config.html)。

| 表的用途 | 推荐名称 | 避免的名称 |
| --- | --- | --- |
| 销售订单 | `sales_order` | `sales_orders`、`order`、`SalesOrder` |
| 订单明细 | `sales_order_item` | `sales_order_items`、`detail`、`order1` |
| 用户资料 | `user_profile` | `user_profiles`、`userinfo`、`yhxx` |
| 用户角色关联 | `user_role` | `user_roles`、`relation`、`user_role_data` |

**字段命名**

字段名应表达数据含义，必要时体现单位或所属业务对象。集合、计量数量与统计结果的命名统一遵守上文“集合与统计语义命名表”；其余常见形式如下。

| 字段语义 | 命名约定 | 示例 |
| --- | --- | --- |
| 关联对象标识 | `<对象>_id` | `user_id`、`order_id` |
| 创建、修改操作者标识 | `created_by_<实体>_id`、`updated_by_<实体>_id` | `created_by_user_id`、`updated_by_account_id` |
| 业务编号 | `<对象>_no` | `order_no`、`payment_no` |
| 事件发生时间 | `<事件>_at` | `paid_at`、`expired_at` |
| 纯日期 | `<含义>_date` | `billing_date` |
| 时长或容量 | 名称中明确单位 | `timeout_ms`、`file_size_bytes` |
| 布尔含义 | 使用明确的判断式名称 | `is_enabled`、`has_attachment` |
| 状态 | 上下文中含义明确 | `payment_status`、`membership_status` |

`name`、`status` 等名称在表内含义明确时可以使用；存在多个不同含义时，应增加业务限定词。

### 1.6 注释要求

表和字段必须使用 `COMMENT` 保存业务说明，以中文为主，必要时保留通用技术术语。注释应说明名称之外的信息，使维护人员能够理解数据的含义和使用边界。

**数据库说明**

每个业务库的设计说明必须记录：

- 所属应用和业务服务。
- 承载的业务范围。
- 维护团队。
- 已明确允许的跨库访问流程。

这些信息记录在服务的数据库设计说明中。表和字段的业务含义通过 DDL 中的 `COMMENT` 保存。

**表注释**

每张业务表必须说明：

1. 保存哪类业务数据。
2. 每一行代表什么。
3. 存在特殊语义时，说明保存的是当前状态、历史记录还是业务快照。

| 表名 | 不充分的注释 | 推荐注释 |
| --- | --- | --- |
| `sales_order` | 订单表 | 销售订单，每行表示一笔订单的当前业务状态 |
| `sales_order_item` | 明细表 | 销售订单明细，每行表示订单中的一个商品明细 |
| `user_membership` | 会员表 | 用户当前会员权益，每个用户一行 |
| `membership_change_record` | 会员记录 | 会员权益变更记录，每行表示一次权益变更 |

示例中的行粒度是对应示例表的设计含义，不代表所有业务必须采用相同模型。

**字段注释**

每个字段必须说明业务含义，并按需要补充以下信息：

| 字段用途 | 注释应补充的内容 |
| --- | --- |
| 标识或编号 | 标识什么对象，属于内部标识还是业务编号 |
| 金额、数量、时长 | 单位，以及必要的币种或计量口径 |
| 状态、分类 | 各取值对应的业务含义 |
| 事件时间 | 对应哪个业务事件，明确注明 UTC |
| 允许 NULL | NULL 代表什么业务含义 |
| 冗余或快照数据 | 来源以及是否随来源数据更新 |
| 特殊值 | 例如 `0`、空字符串等特殊值的明确含义 |

例如：

| 字段 | 注释示例 |
| --- | --- |
| `order_no` | 订单业务编号，用于对外展示和查询 |
| `payment_status` | 支付状态：10待支付，20已支付，30已关闭 |
| `payable_amount` | 应付金额，单位：分，币种：CNY |
| `paid_at` | 支付成功时间，UTC；NULL表示尚未支付 |
| `user_name_snapshot` | 下单时的用户名称快照，不随用户资料更新 |

以上取值、单位和可空性仅用于演示注释写法，具体字段设计在后续部分确定。

**注释维护**

- 字段含义、单位、状态映射或特殊值含义变化时，必须同步更新注释及设计说明。
- 注释不得只重复字段名，例如 `payment_status` 只注释为“支付状态”并不充分。
- 注释不得包含真实个人信息、密码或密钥，示例数据应使用虚构值。
- 维护人员姓名、联系电话、部署环境等易变信息放在维护记录中，避免写入表和字段注释。

## 2. 字段、主键与约束

本章规定字段如何表达业务数据、主键如何生成，以及如何保证数据完整性。命名与注释遵守第 1 章，字符集、比较规则、时间语义和连接配置遵守 [MySQL 数据库基线规范](baseline.md)。

下文的“默认”属于公司设计约定。采用其他方案时，必须在数据库设计说明中记录业务原因、取值范围、约束方式和 Go 映射。

### 2.1 字段类型与取值范围

每个字段必须先明确业务含义、单位、最大取值或长度，再选择类型。不能仅根据一批现有数据决定容量，也不能将所有字符串统一设为 `VARCHAR(255)`。

对象计数、整数计量数量和时长统一采用有符号 `BIGINT`，业务状态和类型编码统一采用有符号 `INT`。这些场景不再按当前数值大小自行选择更小的整数类型，以减少设计分歧、Go 类型转换和后续扩容变更；业务取值范围仍须由应用层单独定义和校验。

本节表格中的 Go 类型表示非空列的基础类型；可空列必须按 2.6 的统一映射处理。

| 数据语义 | 默认或推荐类型 | 选择要求与理由 |
| --- | --- | --- |
| 内部主键、关联对象标识 | 有符号 `BIGINT` | 主键统一由应用通过雪花算法生成，与 Go `int64` 对齐；具体要求见 2.3，关联字段与被关联标识保持一致 |
| 对象计数、整数计量数量 | 有符号 `BIGINT` | 统一映射 Go `int64`，预留累计增长空间；明确业务上限，不能将对象数量与业务编号混用 |
| 业务状态、类型编码 | 有符号 `INT` | 统一映射 Go `int32`，减少枚举类型选择和扩展变更；明确定义各编码的含义及合法取值 |
| 布尔值 | `TINYINT` | 应用层保证只写入 `0`、`1`，必填字段声明 `NOT NULL`；`TINYINT(1)` 本身不限制值域 |
| 可按约定最小货币单位表达的结算金额 | 有符号 `BIGINT` | 默认用整数保存，注释明确单位和币种，例如 CNY 的分；明确最大金额及是否允许负数 |
| 高精度单价、汇率、非整数计量数量、占比 | `DECIMAL(p,s)` | 用于要求精确十进制表示的数值，Go 统一使用 `shopspring/decimal` 的 `decimal.Decimal`；显式确定总位数、小数位数、业务范围与舍入规则 |
| 允许近似误差的测量值、算法评分等 | `DOUBLE` | Go 统一使用 `float64`，由应用明确单位、业务范围及允许的误差；不得用于要求精确的金额计算 |
| 业务编号、名称、普通短文本 | `VARCHAR(n)` | 根据业务契约明确长度；外部编号即使只含数字，也应在需要保留前导零等语义时使用字符串 |
| 确有定长语义的字符串 | `CHAR(n)` | 仅在长度固定且已明确补空格、读取时尾空格处理的情况下使用，其他场景默认 `VARCHAR(n)` |
| 长文本 | 按容量选择 `TEXT` 系列 | 明确大小上限和读取场景；频繁查询的核心属性不能全部藏入长文本 |
| 原始字节数据 | `VARBINARY(n)` 或按容量选择 `BLOB` 系列 | 与文字内容区分，明确字节长度；大附件默认存对象存储，数据库保存引用及必要元数据 |
| 事件发生时间 | `DATETIME(3)` | 默认毫秒精度，所有值表示 UTC；需要微秒时明确采用 `DATETIME(6)`，禁止 `TIMESTAMP` 列类型 |
| 纯日期 | `DATE` | 非空列使用 `time.Time`，可空列按 2.6 使用 `sql.NullTime`；均仅承载生日、账期日期等年月日，不按事件时刻做时区转换 |
| 时长 | 有符号 `BIGINT` | 统一映射 Go `int64`，在名称及注释中明确单位，例如 `timeout_ms` |
| 有明确结构的附属数据 | `JSON` | 限于适合整体保存的附属结构，必须定义内容、大小和读写契约，不能作为通用字段收纳箱 |

**数值与精度**

- 整数统一采用有符号类型，不声明 `UNSIGNED`。非负等业务取值要求由应用层校验，不因业务不允许负数而改用无符号类型，保持数据库与 Go 映射一致。整数范围参见 [MySQL 整数类型](https://dev.mysql.com/doc/refman/8.4/en/integer-types.html)。
- 浮点字段统一使用 MySQL `DOUBLE` 对应 Go `float64`，不采用 `FLOAT` 或 `float32`，也不使用 `DOUBLE(M,D)` 声明小数位。允许近似误差的场景才可采用浮点数，参见 [MySQL 浮点类型说明](https://dev.mysql.com/doc/refman/8.4/en/floating-point-types.html)。
- 禁止使用浮点数保存或计算要求精确的金额、单价、汇率和结算比例。按整数货币单位保存的金额继续使用 `BIGINT`、`int64`；需要精确小数的字段使用 `DECIMAL(p,s)`、`decimal.Decimal`。
- `DECIMAL(p,s)` 的 `p` 为总位数，`s` 为小数位数。例如 `DECIMAL(12,2)` 可保存 10 位整数和 2 位小数；不能只写 `DECIMAL` 而省略设计精度。参见 [MySQL 定点类型](https://dev.mysql.com/doc/refman/8.4/en/fixed-point-types.html)。
- 写入前必须校验数值范围并按业务约定处理精度。`DECIMAL` 精确存储不代表超出小数位的输入一定报错，严格模式下也可能发生舍入；不能依赖数据库替代业务精度校验。参见 [MySQL 舍入规则](https://dev.mysql.com/doc/refman/8.4/en/precision-math-rounding.html)。
- 状态码一经使用，不得改成另一种业务含义或回收给其他状态。业务状态使用 `INT` 编码，合法值及状态流转由应用层统一定义和校验，不使用 MySQL `ENUM`、`SET` 承载业务状态；可维护的分类可以建立字典关系，由应用层校验关联。

**字符串与结构化数据**

- `VARCHAR(n)` 的 `n` 表示字符数，字节占用还取决于字符集；长度设计必须同时考虑行大小和索引字节限制。普通字符字段继承表的 `utf8mb4` 与 `utf8mb4_0900_bin`，不得用截断文本的方式掩盖输入超长。参见 [MySQL CHAR 与 VARCHAR](https://dev.mysql.com/doc/refman/8.4/en/char.html)。
- 单个字段表达一个明确的业务属性。需要分别查询、约束或更新的稳定属性，应设计为独立列；订单明细、用户角色等具有独立关系或生命周期的数据，应设计为明细表或关联表。
- 禁止在字符串中用逗号拼接多个对象 ID。确需 JSON 集合时，必须说明元素结构、是否有序、去重规则、数量上限，以及 SQL `NULL`、JSON `null`、`{}`、`[]` 各自的含义。MySQL 能查询 JSON，是否采用 JSON 仍需根据业务设计，参见 [MySQL JSON 类型](https://dev.mysql.com/doc/refman/8.4/en/json.html)。
- 冗余或快照字段必须说明数据来源和更新规则。例如下单时的用户名称快照应保留当时值，不能随用户改名同步覆盖。

**时间精度**

事件时间沿用基线的 UTC 语义，默认显式声明 `DATETIME(3)`。应用写入前先转换 UTC，再统一截断到毫秒；使用 `DATETIME(6)` 时对齐到微秒。不得依赖操作系统时区，也不得以 Unix 时间整数替代统一事件时间列。

MySQL 省略小数秒精度时默认为 0，高精度时间写入低精度列时默认会舍入，不能认为严格模式会阻止这一行为。数据库生成时间时，`CURRENT_TIMESTAMP(p)` 的精度必须与列一致。参见 [MySQL 小数秒规则](https://dev.mysql.com/doc/refman/8.4/en/fractional-seconds.html)。

### 2.2 可空性与默认值

可空性由业务含义决定。必须存在的值使用 `NOT NULL`；未知、未发生或不适用的值可以使用 `NULL`，但字段注释必须明确具体含义。禁止要求所有字段一律非空，也禁止用同一个占位值混淆多种状态。

允许 `NULL` 的列，Go 持久化模型统一使用 2.6 规定的 `sql.Null*` 类型；可空 `DECIMAL` 使用 `decimal.NullDecimal`，不采用字段指针或自定义可空封装。

| 情况 | 规范选择 | 示例与理由 |
| --- | --- | --- |
| 业务必须提供且没有真实默认值 | `NOT NULL`，不设置 `DEFAULT` | 订单业务编号、必须确认的应付金额；遗漏写入时应失败，不能自动补空串或零 |
| 业务初始值确定 | `NOT NULL DEFAULT <初始值>` | 初始订单计数为 `0`，支付初始状态为约定的待支付编码 |
| 事件尚未发生 | `NULL DEFAULT NULL` | 未支付的 `paid_at` 为 `NULL`，支付成功后写入真实 UTC 时间 |
| 可选信息尚未提供 | `NULL DEFAULT NULL` | 仅在业务确实区分“未提供”和“提供了空文本”时采用，并说明区别 |
| 空集合是已知有效状态 | 明确约定空集合值 | 空数组 `[]` 表示已知没有元素，不能与“内容未知”的 `NULL` 混为一谈 |

- `0`、空字符串、空集合都是具体值，只有具有明确业务含义时才可使用。不存在关联对象时，使用有说明的 `NULL`，不以 `0` 伪造对象标识。
- 必填字符串除了 `NOT NULL`，还必须检查是否为空、是否允许全空格等规则；`NOT NULL` 本身不禁止空字符串。
- 必填输入必须在应用入口区分“未提供”和“明确为零值”。`NOT NULL` 且无默认值可以拒绝 SQL 遗漏字段，却无法识别 ORM 主动补入的合法 `0` 或空字符串，不能代替输入完整性校验。
- 对已设置默认值的业务字段，插入时省略该字段或显式使用 `DEFAULT` 会采用默认值；显式写入 `NULL` 时，可空字段保存 `NULL`，`NOT NULL` 字段在本规范的严格模式下报错。参见 [MySQL 默认值规则](https://dev.mysql.com/doc/refman/8.4/en/data-type-defaults.html)。
- 禁止使用零日期、Go 零时间或约定的遥远日期代替“未发生”。例如未支付时间使用 `NULL`，不能写成 `0000-00-00`、`0001-01-01` 或 `1970-01-01`。
- 创建时间等自动值必须同时确定维护方，按 2.5 执行。业务事件时间不能仅因为列存在，就默认取插入时的当前时间。

以下为订单表的列定义片段，编号长度和状态取值仅用于说明本节规则：

```sql
order_no VARCHAR(64) NOT NULL COMMENT '订单业务编号，用于对外展示和查询',
payable_amount BIGINT NOT NULL COMMENT '应付金额，单位：分，币种：CNY',
payment_status INT NOT NULL DEFAULT 10 COMMENT '支付状态：10待支付，20已支付，30已关闭',
paid_at DATETIME(3) NULL DEFAULT NULL COMMENT '支付成功时间，UTC；NULL表示尚未支付'
```

其中，免费订单的金额可以合法为 `0`，但必须由业务明确写入；不能因默认值为零而把漏传金额当作免费订单。

### 2.3 主键与 ID 生成

**统一主键方案**

- 每张业务表必须使用单列 `id` 作为主键，包括明细表和关联表。ID 由应用通过公司统一的雪花算法组件生成，数据库类型为有符号 `BIGINT`，Go 类型为 `int64`。
- 主键列使用 `BIGINT NOT NULL`，不得声明 `AUTO_INCREMENT`，不得设置数据库生成默认值。应用必须在写入前取得并显式写入 ID，不依赖数据库分配或插入后的 `LastInsertId` 回填。
- ID 必须为正数，由统一发号组件和应用写入入口验证，发现 `id <= 0` 时中止创建。`0` 仅表示应用中“尚未分配”，不得写入业务表。对象主键写入后不得修改，也不得主动复用已删除对象的主键。
- 主键只承担内部记录标识。订单号等业务编号独立建列并按业务范围设置唯一约束，不能用可变业务编号替代雪花主键。
- 关联表仍须定义业务唯一性。例如用户角色关联除独立 `id` 外，还需对 `(user_id, role_id)` 设置唯一约束，雪花主键不能防止重复关联。

以 `sales_order` 为例，主键定义片段如下，ID 的来源和正数要求由应用层保证：

```sql
id BIGINT NOT NULL COMMENT '内部主键，应用通过雪花算法生成',
PRIMARY KEY (id)
```

应用在入库前取得 ID，便于提前建立主从记录和跨库记录的关联；数据库继续使用整数主键承载数据和索引。InnoDB 的主键组织方式参见 [InnoDB 聚簇索引](https://dev.mysql.com/doc/refman/8.4/en/innodb-index-types.html)。

**统一生成组件与唯一性范围**

同一应用、同一环境下的所有业务表共用一个 ID 分配范围，节点管理覆盖全部服务副本、后台任务和导入工具，保证该范围内新生成的 ID 跨表不重复。不得按表或按服务各自使用相同节点编号独立发号。

| 项目 | 约束 |
| --- | --- |
| 编码方案 | 统一起始时间、时间单位和位分配，输出必须处于正 `int64` 范围，最多使用 63 个有效位；明确时间有效期、节点容量和每个时间片的发号容量，不得由各服务自行修改 |
| 组件实例 | 同一进程共享并发安全的发号器，不为每张表或每次创建记录重新构造独立序列状态 |
| 节点标识 | 同一分配范围内，每个独立发号器的完整节点标识必须唯一，由统一机制分配；不得用未经避碰保证的随机值、IP 取模等方式分配 |
| 扩缩容与重启 | 节点编号分配必须覆盖扩缩容、重启和故障恢复；采用租约时，租约失效必须停止发号，编号复用前必须防止旧发号器继续运行及相同时间片内的序列重放 |
| 时钟回拨 | 组件必须统一处理，等待至安全时刻或拒绝发号；重启后仍须保证安全，不能在无法保证唯一性时继续生成 |
| 序列或时间容量耗尽 | 当前时间片序列耗尽时等待后续时间片或返回错误；时间有效期耗尽时停止发号，不得截断或回绕已有编码 |
| 发号失败 | 中止本次创建并返回明确错误，不得用 `0`、当前时间、随机数或数据库自增作为降级方案 |

雪花算法中的时间、节点和序列结构可参考 [Snowflake Go 实现说明](https://github.com/bwmarrin/snowflake)。本文不指定具体依赖库或位数配置，组件选型和配置必须统一维护，不能直接采用各依赖库的默认节点号。

跨应用或环境汇总、同步、迁移数据且需要保留原 ID 时，必须提前协调发号配置和节点范围，或制定包含关联引用的 ID 重映射方案。给分配范围起不同名称，并不能使生成的数字自动互不重复。

**写入、重试与使用边界**

- 所有创建入口都必须先分配 ID，包括批量插入、关联创建、脚本和导入任务；批量操作须为每条新记录分别分配。仅在某个 ORM 钩子中生成 ID，不足以覆盖所有入口。
- 同一对象的写入重试应复用已分配的 ID，不能将该 ID 再分配给其他对象。遇到重复主键或提交结果不确定时，按原 ID 和业务幂等键核对，确认对应同一业务操作后再处理，不能直接换一个新 ID 重复创建。
- 雪花 ID 唯一不等于业务请求幂等。订单号、支付事件编号等业务唯一约束仍按 2.4 设置。
- 雪花 ID 不保证连续、跨节点严格递增或事务提交顺序；不能用 ID 差值计算数量，也不能用其中的时间信息替代业务 `DATETIME` 字段。禁止使用 `MAX(id) + 1` 或仅用当前毫秒数自行拼接主键。
- 历史表整改必须单独核对已有主键和关联引用，不能将改用雪花算法理解为直接批量重写已有对象的主键。

关联字段必须与被关联标识采用相同类型、符号属性及业务编码方式；字符串关联键还须保持字符集和比较规则一致。外部系统的原始标识应单独保存，不能未经约定与本系统内部 `id` 混用。

### 2.4 业务唯一性与完整性约束

MySQL 保留字段类型、非空、默认值、主键和唯一性等存储约束。关联关系、业务取值范围和状态流转统一由应用层维护；所有业务表禁止定义物理外键和 `CHECK` 约束，也不得通过触发器或存储过程维护这些业务校验。

**业务唯一性**

每个业务唯一键必须说明对象、作用范围、组成字段，以及删除后是否允许复用。同一应用共享 RDS 实例，不代表所有业务编号自动具有全局唯一性。

| 业务约定 | 对应约束 |
| --- | --- |
| 订单号在本订单表中唯一 | 对 `order_no` 设置唯一约束 |
| 多租户系统中，订单号仅在租户内唯一 | 对 `(tenant_id, order_no)` 设置联合唯一约束，查询和写入同时携带租户条件 |
| 同一用户不能重复绑定同一角色 | 对 `(user_id, role_id)` 设置联合唯一约束 |
| 同一业务事件不能重复处理 | 对能唯一标识该事件的来源及事件编号等字段设置唯一约束，配合事务保证处理幂等 |

- 必须由数据库唯一约束兜底。应用可以提前检查并返回友好提示，但“先查询不存在，再插入”不能保证并发下唯一，程序仍须处理重复键错误。
- 参与业务唯一性的字段默认 `NOT NULL`。MySQL 唯一约束允许多个 `NULL`，不能用可空字段来保证本应唯一的业务对象。参见 [MySQL CREATE TABLE 唯一约束说明](https://dev.mysql.com/doc/refman/8.4/en/create-table.html)。
- 字符串唯一性还取决于规范化与比较规则。账号等字段必须统一写入和查询的规范化方式，遵守基线规定，不能仅凭“建了唯一索引”认定业务等价规则正确。
- 默认业务编号在软删除后也不复用。确需只约束有效记录时，必须另外设计可验证的唯一键方案，并覆盖重复删除、重新创建和历史保留场景。

例如，`UNIQUE(order_no, deleted_at)` 不能保证未删除记录的订单号唯一，因为未删除记录的 `deleted_at` 都为 `NULL`；改成 `UNIQUE(order_no, is_deleted)` 也无法容纳同编号的多条已删除历史。不得将其中任一形式作为通用软删除唯一性模板。

唯一约束保证的是对应键不重复，不能单独证明一次购买会员的订单与会员权益已经同步更新，跨库流程仍按 1.3 的同一事务及幂等约定执行。

**关联关系由应用层维护**

业务关联必须在设计说明中记录父子对象、关联字段、是否必选、删除规则及维护入口。

- 所有业务库表统一禁止物理外键，包括同库内的关联。仍可用普通关联字段和 ORM 逻辑关系映射表达关系，相关列遵守 2.3 的类型一致要求；存在 `user_id` 等列不代表数据库会检查关联对象是否存在。
- 创建或修改关联时，由应用校验目标对象是否存在、是否允许建立该关系，以及租户等业务范围是否一致；拒绝不符合规则的写入。
- 删除、软删除或解除关联时，由应用明确处理依赖记录，按业务规则选择拒绝操作、保留历史或显式修改相关数据，不依赖数据库自动连带处理。
- 需要严格一致的父子关系，应统一创建与删除入口，在同一事务内采用父记录锁定、删除前关联检查等相互配合的并发规则；不能只在普通查询中确认父记录存在，就认定后续插入安全。
- 跨库流程涉及的关联维护仍须使用 1.3 规定的受控事务。关联数据允许暂时不一致时，必须明确允许范围、修复方式及维护方，不能将其当作默认行为。

**取值与业务状态由应用层校验**

合法取值、字段之间的业务关系和状态流转规则，必须在应用的统一业务模块中定义并执行。校验应覆盖创建和更新，不能只校验 HTTP 参数或只检查 Go 字段类型。

| 规则 | 应用层维护要求 |
| --- | --- |
| 雪花主键为正数 | 发号成功后及写入前验证 `id > 0`，不合法时拒绝创建；数据库 `NOT NULL` 不会拒绝数值 `0` |
| 布尔值 | 写入值仅为 `0`、`1`，原始 SQL、脚本等入口执行同样校验 |
| 金额、数量和比例范围 | 根据业务定义上下限、单位及精度，例如应付金额不小于零；不能对所有数值机械套用同一条件 |
| 状态、类型编码 | Go 业务枚举及统一校验规则明确合法编码，拒绝未定义值；自定义枚举类型本身不保证取值合法 |
| 多字段业务关系 | 明确并校验字段组合是否合法，例如已支付订单必须具有有效的支付成功时间 |
| 状态流转 | 同时校验目标状态和原状态到目标状态是否允许，不能只检查新状态属于合法编码 |

- 并发状态变更必须使用带旧状态或版本条件的更新，或在事务内锁定记录后校验并更新；执行后检查错误和实际影响行数，不能只做更新前的普通查询。
- 同一业务的关联与取值规则必须覆盖应用、后台任务、脚本、导入和数据修复等所有写入入口。优先复用统一业务模块，不能复用时执行等效校验，不依赖数据库业务约束兜底。
- 字段注释和设计说明应记录取值含义及关键规则，应用实现与之保持一致。调整规则时，同步检查相关写入入口和历史数据兼容性。

### 2.5 通用字段与维护规则

通用字段按表的用途选择，不能给所有表无条件套用同一个字段模板。

| 字段 | 推荐定义 | 适用范围与维护规则 |
| --- | --- | --- |
| `created_at` | `DATETIME(3) NOT NULL` | 默认业务表记录本行创建时间，UTC；创建后不修改，事件发生时间另设业务字段 |
| `updated_at` | `DATETIME(3) NOT NULL` | 默认用于可变业务实体，创建时与 `created_at` 相同，后续有效业务修改时更新；只追加记录可不设置 |
| `deleted_at` | `DATETIME(3) NULL DEFAULT NULL` | 仅在业务对象需要软删除时设置；1.4.3 所述当前关系表禁止使用。UTC，`NULL` 表示未删除，非空表示删除时刻 |
| `version` | `BIGINT NOT NULL DEFAULT 0` | 仅在采用版本式并发控制时设置，每次受保护修改加一，所有相关写入路径必须遵守 |
| `created_by_<实体>_id`、`updated_by_<实体>_id` | 有符号 `BIGINT`，按业务确定可空性 | 仅在需要记录操作者时设置；字段名必须明确实际引用的业务实体，每列固定指向一种实体 |
| `tenant_id` | 与租户主键一致的非空类型 | 仅用于需要按租户隔离的数据表；不是所有业务表都需要，具体要求见下文 |

操作者字段必须在实际表设计中明确实体名称，使用单数并遵守 1.5 的业务概念用词约定。例如，引用用户时使用 `created_by_user_id`、`updated_by_user_id`，引用账户时使用 `created_by_account_id`、`updated_by_account_id`。禁止直接使用 `created_by_id`、`updated_by_id` 等未说明实体的名称。

字段注释必须说明实际引用的库表及标识列，应用按 2.4 维护关联。同一列不得根据操作来源改为保存另一种实体的 ID。若字段仅记录用户操作者，且允许非用户操作，则可约定该情况为 `NULL` 并注明含义，不得用 `0` 代替关联标识。

**租户与 tenant_id**

租户是共用一套系统、但业务数据和权限需要独立隔离的一方，通常是企业、商户或组织。一个租户可以有多个用户；租户不等于用户、业务服务或数据库。

例如，商户 A、B 共用一套商户管理系统，各自有员工、客户和订单。两者共用 `order_service.sales_order` 表时，通过 `tenant_id` 标记订单归属，普通业务访问只能操作所属租户的数据。以下 ID 为简写：

| id | tenant_id | order_no |
| --- | --- | --- |
| 10001 | 1001（商户 A） | ORDER001 |
| 10002 | 2001（商户 B） | ORDER001 |

`tenant_id` 不是所有业务表的必填通用字段。只有需要按租户区分归属并隔离访问的数据表才设置；没有租户隔离需求的表、明确的全局共享数据，不要求增加该字段。

设置 `tenant_id` 的表必须同时满足：

- 普通业务的查询、修改和删除由应用限定租户范围，租户身份须经服务端验证，不能仅凭客户端传入的 `tenant_id` 授予访问权限。
- 唯一约束遵循业务范围。例如订单号仅在同一商户内唯一时，约束 `(tenant_id, order_no)`，因此 A、B 可以各有一个 `ORDER001`。
- 租户内的关联由应用校验归属，不能将 A 的订单关联到 B 的客户；仅增加一列不会自动实现上述隔离。

**时间维护方**

创建时间和修改时间默认由应用统一维护：一次写入先取得统一的 UTC 时间，并对齐列精度。`created_at` 创建后保持不变，`updated_at` 随业务修改维护；导入和数据修复需要保留历史时间时，必须明确来源。

使用 GORM 自动维护时间时，`NowFunc` 用于提供自动填写创建、修改时间所需的“当前时间”。默认采用 `DATETIME(3)`，因此统一初始化时配置为 UTC、毫秒精度：

```go
NowFunc: func() time.Time {
    return time.Now().UTC().Truncate(time.Millisecond)
},
```

其中，`time.Now()` 获取当前时刻，`.UTC()` 转换为 UTC 表示，`.Truncate(time.Millisecond)` 截去毫秒之后的小数位，例如 `.123456` 变为 `.123`。

以下按应用维护时间的方案说明，前提是模型中定义了 `CreatedAt`、`UpdatedAt`，已启用 GORM 自动时间维护，且未显式排除相关字段：

| 操作 | 时间维护方式 |
| --- | --- |
| 普通模型的 `Create` | 自动为尚未赋值的 `CreatedAt`、`UpdatedAt` 填写 `NowFunc` 返回的时间；已明确赋值的时间保留原值 |
| 普通模型的 `Update`、`Updates`，包括 `Updates(map)` | 自动维护 `UpdatedAt`；应用显式提供时间时，须确保该写法实际采用预期值 |
| `Create(map)` | 应用显式提供需要的创建、修改时间 |
| `UpdateColumn`、`UpdateColumns` | 跳过自动时间维护，应用显式提供需要的修改时间 |
| 原始写入 SQL，如通过 `Exec` 执行插入或更新 | 应用在 SQL 参数中显式提供需要的时间 |

`NowFunc` 不会统一转换所有时间字段。手动提供的支付时间等业务事件时间，仍须由应用先转换 UTC 并对齐列精度；使用 `DATETIME(6)` 时按微秒精度处理。参见 [GORM 时间函数配置](https://gorm.io/docs/gorm_config.html#NowFunc)、[自动时间字段约定](https://gorm.io/docs/conventions.html#Timestamp-Tracking)、[Map 创建说明](https://gorm.io/docs/create.html#Create-From-Map)和 [跳过时间追踪的更新](https://gorm.io/docs/update.html#Without-Hooks-Time-Tracking)。

确需数据库维护时，可以显式使用 `DEFAULT CURRENT_TIMESTAMP(3)`、`ON UPDATE CURRENT_TIMESTAMP(3)`，但必须在表设计中说明，确保所有连接为 UTC，并让 ORM 正确省略由数据库生成的列。同一列不混用多套自动维护逻辑；只关闭 ORM 时间钩子，却仍写入 Go 零时间，不会自动获得数据库默认值。参见 [MySQL 自动时间字段说明](https://dev.mysql.com/doc/refman/8.4/en/timestamp-initialization.html)。

`updated_at` 不代表事务提交时间，也不保证唯一或严格递增，不能代替事件顺序、审计历史或版本控制。

**软删除与版本控制**

- 软删除必须同时定义普通查询过滤、重复删除、是否恢复、关联数据处理及唯一键复用规则。增加 `deleted_at` 一列不代表这些行为已经实现；软删除也不等于物理清除数据。
- `deleted_at` 在持久化模型中统一使用 `sql.NullTime`。它只表达时间是否为 `NULL`，不会自动启用 GORM 的软删除行为；应用必须显式写入删除时间，并在普通查询中添加 `deleted_at IS NULL` 等过滤条件，不能认为调用 `Delete` 就会自动执行软删除。参见 [GORM 软删除说明](https://gorm.io/docs/delete.html#Soft-Delete)。
- 使用 `version` 时，修改条件必须包含读取到的旧版本，更新时同时递增。只有列名叫 `version`，不会自动获得乐观锁保护。

以下 SQL 仅演示用户资料的版本式更新，`?` 为参数占位符：

```sql
UPDATE user_service.user_profile
SET user_name = ?,
    updated_at = ?,
    version = version + 1
WHERE id = ? AND version = ?;
```

执行后先检查错误，再检查影响行数；使用 GORM 时检查 `Error` 和 `RowsAffected`。影响行数为 `0` 表示本次更新未成功，可能是记录不存在、版本变化或其他条件不满足，须核对后返回冲突或按业务规则重试，不能直接视为成功。

### 2.6 Go 与 GORM 映射

数据库定义和 Go 模型必须保持存储范围、精度、可空性及默认行为一致，业务合法取值与状态规则按 2.4 在应用层校验。不能根据 Go 类型或 ORM 自动推导结果，倒推业务表应该采用什么结构。

下表列出非空列的基础映射；允许 `NULL` 的列必须使用后文“可空字段统一映射”中的类型。

| MySQL 字段 | 统一 Go 类型 | 映射要求 |
| --- | --- | --- |
| 有符号 `BIGINT` | `int64` | 用于雪花主键、关联标识、整数金额、对象计数、整数计量数量和时长；不使用平台相关的 `int` 或无符号类型替代 |
| 有符号 `INT` | `int32` | 用于业务状态和类型编码；业务枚举的底层类型也统一为 `int32`，合法值由应用统一定义并校验 |
| 应用限定取值为 `0`、`1` 的 `TINYINT` 布尔列 | `bool` | 由应用校验写入值，不能依赖 `TINYINT` 类型自动限制为布尔值 |
| `VARCHAR`、`CHAR`、`TEXT` | `string` | 单独校验业务长度；Go `len` 返回字节数，不能直接作为 Unicode 字符数 |
| `VARBINARY`、`BLOB` | `[]byte` | 按字节语义处理，不隐式当作文字转换 |
| `DOUBLE` | `float64` | 用于允许近似误差的数值，GORM 显式指定 `type:double`，不以 `float32` 降低精度 |
| `DECIMAL(p,s)` | `decimal.Decimal` | 统一使用 `github.com/shopspring/decimal`，GORM 显式指定 `type:decimal(p,s)`，不得用浮点类型承接精确十进制值 |
| `DATETIME(3)`、`DATETIME(6)` | `time.Time` | 配合基线的 `parseTime=true`、`loc=UTC` 与会话 UTC，写入前统一转换和对齐精度 |
| `DATE` | `time.Time` | 仅使用年月日，保持日历日期语义，不把日期当作 UTC 事件时刻跨时区转换 |
| `JSON` | 明确结构的类型或项目统一 JSON 封装 | 定义序列化、反序列化、兼容升级和缺失值语义；不能只加 `type:json` 就假定普通结构体会自动序列化 |

**可空字段统一映射**

可空性是在基础类型之外表达“是否有值”的要求。Go 持久化模型必须按下表映射，不再使用字段指针或业务自定义可空封装；`sql.Null*` 是标准库相关类型的统称。

| 可空 MySQL 列 | 统一 Go 类型 | 映射要求 |
| --- | --- | --- |
| 有符号 `BIGINT` | `sql.NullInt64` | `Int64` 保存数值，`Valid` 区分 `NULL` 与包括 `0` 在内的具体数值 |
| 有符号 `INT` | `sql.NullInt32` | 状态、类型编码仍按应用业务枚举校验 |
| 布尔语义的 `TINYINT` | `sql.NullBool` | 区分 `NULL`、`false` 和 `true`，应用保证数据库值为 `0`、`1` |
| `DOUBLE` | `sql.NullFloat64` | 用于允许近似误差的可空数值 |
| `VARCHAR`、`CHAR`、`TEXT` | `sql.NullString` | 区分 `NULL`、空字符串和非空文本 |
| `DATETIME(3)`、`DATETIME(6)` | `sql.NullTime` | 有值时仍须使用 UTC 并对齐列精度，连接保持 `parseTime=true` |
| `DATE` | `sql.NullTime` | 有值时底层使用 `time.Time`，仅承载年月日，保持日历日期语义 |
| `DECIMAL(p,s)` | `decimal.NullDecimal` | 使用 `shopspring/decimal` 提供的可空类型，禁止用浮点可空类型代替 |
| `VARBINARY`、`BLOB` | `sql.Null[[]byte]` | 使用当前 Go 1.25 支持的标准库泛型，GORM 显式声明对应二进制列类型 |
| `JSON` | `sql.NullString` | GORM 显式声明 `type:json`，内容为经应用校验的已序列化 JSON 文本，不叠加 `serializer:json` |

`sql.Null*`、`sql.Null[T]`、`decimal.Decimal` 和 `decimal.NullDecimal` 已提供 `sql.Scanner`、`driver.Valuer`，GORM 可以自动完成数据库读写转换，不需要业务自行编写这些映射。模型中仍须显式选择对应类型，ORM 不会自动将普通 `string`、`time.Time` 改成可空类型。参见 [Go 可空类型](https://pkg.go.dev/database/sql#NullString)、[标准库泛型 Null](https://pkg.go.dev/database/sql#Null)、[shopspring/decimal 类型说明](https://pkg.go.dev/github.com/shopspring/decimal#NullDecimal)和 [GORM 模型说明](https://gorm.io/docs/models.html)。

`Valid` 的含义统一如下：

- `Valid=false`：表示 SQL `NULL`，读取方不得将内部值当作业务数据使用；字段参与写入时，其值转换为 SQL `NULL`。
- `Valid=true`：表示存在具体值，即使这个值是 `0`、`false` 或空字符串，也不能按 `NULL` 处理。
- `Valid` 不表示业务校验是否通过。有值时仍须按 2.4 校验合法范围、关联关系和状态规则。

例如：

| Go 值 | 对应的数据库值 |
| --- | --- |
| `sql.NullString{Valid: false}` | SQL `NULL` |
| `sql.NullString{String: "", Valid: true}` | 空字符串 |
| `sql.NullString{String: "备注内容", Valid: true}` | 文本“备注内容” |
| `sql.NullInt64{Int64: 0, Valid: true}` | 数字 `0` |
| `sql.NullBool{Bool: false, Valid: true}` | 布尔值 `false`，按本规范写入为 `0` |
| `decimal.NullDecimal{Decimal: decimal.Zero, Valid: true}` | 精确十进制数 `0` |

二进制列的有效空值必须使用 `sql.Null[[]byte]{V: []byte{}, Valid: true}`，不能用 nil 字节切片表达非空数据。可空 JSON 的 `Valid=false` 表示 SQL `NULL`；`String: "null", Valid: true` 表示 JSON `null`，`String: "{}", Valid: true` 表示空对象，三者含义不同。

**GORM 读写 NULL 示例**

以下以用户资料表的备注列说明，其他字段按实际设计补充。列定义不设置业务默认值：

```sql
remark VARCHAR(200) NULL DEFAULT NULL COMMENT '备注；NULL表示未提供，空字符串表示已提供空内容'
```

对应模型示例：

```go
import (
    "database/sql"
    "time"
)

type UserProfile struct {
    ID        int64          `gorm:"column:id;type:bigint;primaryKey;autoIncrement:false"`
    Remark    sql.NullString `gorm:"column:remark;type:varchar(200)"`
    CreatedAt time.Time      `gorm:"column:created_at;type:datetime(3);not null"`
    UpdatedAt time.Time      `gorm:"column:updated_at;type:datetime(3);not null"`
}
```

创建时，`id` 已由统一雪花组件生成并验证为正数。以下片段显式表示备注为 `NULL`；创建和修改时间按 2.5 自动维护：

```go
record := UserProfile{
    ID:     id,
    Remark: sql.NullString{Valid: false},
}
if err := db.Create(&record).Error; err != nil {
    return err
}
```

查询时，GORM 自动填充 `Remark.String` 和 `Remark.Valid`。读取方先检查查询错误，再检查 `loaded.Remark.Valid`：为 `false` 时按 SQL `NULL` 处理，为 `true` 时才使用 `loaded.Remark.String`，该字符串也可能为空：

```go
var loaded UserProfile
if err := db.First(&loaded, "id = ?", id).Error; err != nil {
    return err
}
```

将已有备注清为 `NULL` 时，必须显式指定更新列。以下片段通过 `nil` 写 SQL `NULL`，并维护 UTC 修改时间：

```go
result := db.Model(&UserProfile{}).
    Where("id = ?", id).
    Updates(map[string]any{
        "remark":     nil,
        "updated_at": time.Now().UTC().Truncate(time.Millisecond),
    })
if result.Error != nil {
    return result.Error
}
```

调用方仍须按业务检查 `result.RowsAffected`。`Updates(struct)` 可能跳过全零的可空结构体，不能仅赋值 `sql.NullString{}` 就假定数据库已清空。带 GORM `default` 标签的字段也可能因零值触发默认行为；需要明确写入 `NULL` 时，应使用上述显式更新方式或显式构造插入列和值。参见 [GORM 更新规则](https://gorm.io/docs/update.html#Updates-multiple-columns)和 [GORM 创建默认值规则](https://gorm.io/docs/create.html#Default-Values)。

上述类型约束用于数据库持久化模型；接口中的“未提供字段”和“明确清空字段”仍需分别表达，不能都用同一个 `Valid=false` 混指。

**DOUBLE 与 DECIMAL 映射示例**

以下 SQL 仅为列定义片段，Go 模型仅展示主键与相关字段，其他业务和通用字段按实际表设计补充。商品单价需要精确十进制表示，算法质量评分允许近似误差，列定义片段如下：

```sql
unit_price DECIMAL(18,6) NOT NULL COMMENT '商品单价，单位：元，币种：CNY，最多6位小数',
quality_score DOUBLE NOT NULL COMMENT '算法质量评分，允许近似误差，范围0至1'
```

GORM 字段映射为：

```go
import "github.com/shopspring/decimal"

type ProductSku struct {
    ID           int64           `gorm:"column:id;type:bigint;primaryKey;autoIncrement:false"`
    UnitPrice    decimal.Decimal `gorm:"column:unit_price;type:decimal(18,6);not null"`
    QualityScore float64         `gorm:"column:quality_score;type:double;not null"`
}
```

精确十进制数从十进制字符串或精确整数构造，不能先通过浮点运算再转成 `decimal.Decimal`。以下写入片段中，`id` 已由统一雪花组件生成，实际业务输入须先完成范围和精度校验：

```go
unitPrice, err := decimal.NewFromString("12.345678")
if err != nil {
    return err
}

record := ProductSku{
    ID:           id,
    UnitPrice:    unitPrice,
    QualityScore: 0.93,
}
return db.Create(&record).Error
```

查询时，GORM 会将 `DECIMAL` 值读入 `UnitPrice`、将 `DOUBLE` 值读入 `QualityScore`。十进制运算使用库提供的 `Add`、`Mul` 等方法，不使用 Go 的 `+`、`*` 运算符；除法等运算还须明确结果精度和舍入规则。

`DECIMAL(18,6)` 只是本示例的容量，不是所有字段的统一精度。自动映射不负责业务范围、小数位和舍入校验，也不代表目标数据库已经具备这些列定义；应用按 2.1、2.4 校验，实际 DDL 按受控 SQL 迁移维护。

**GORM 定义与写入规则**

- 显式核对表名、`column`、类型、长度、精度、可空性和主键生成方式。所有业务模型的雪花主键必须声明 `autoIncrement:false`，数据库 DDL 同时禁止 `AUTO_INCREMENT`。
- GORM 初始化必须设置 `DisableForeignKeyConstraintWhenMigrating: true`。

  该配置仅阻止 GORM 建表、迁移时自动创建外键，不删除已有外键；手写迁移 SQL 仍禁止定义物理外键。
- 模型不得通过 `check` 标签生成 `CHECK` 约束，参见 [GORM 约束配置](https://gorm.io/docs/constraints.html)。
- 不直接将 `gorm.Model` 作为所有业务模型的统一基类：它包含 `uint` 类型主键和软删除字段等预设，不符合本规范统一的主键方案及按需字段要求。参见 [GORM 模型说明](https://gorm.io/docs/models.html)。
- SQL `NULL`、字段未提供、Go 零值是不同状态。禁止用 `time.Time{}` 表达“尚未支付”，也不能只靠普通 `bool` 区分“未提供”与“明确为 false”。
- `Create` 中带 `default` 标签的字段，其 `0`、`false`、空字符串等零值可能被默认值替代。需要明确写入零值或 SQL `NULL` 时，使用符合上述类型约定的值并显式构造写入列和值，核对最终 SQL，不改用字段指针或自行增加可空封装。参见 [GORM 创建时的默认值](https://gorm.io/docs/create.html#Default-Values)。
- `Updates(struct)` 默认忽略零值。需要将字段更新为 `0`、`false` 或空字符串时，使用明确的 `map` 或 `Select` 指定字段；写入 SQL `NULL` 时也必须显式表达。参见 [GORM 更新字段规则](https://gorm.io/docs/update.html#Updates-multiple-columns)。

主键映射示例如下，仅展示 ID 字段，其他业务字段按实际设计补充：

```go
type SalesOrder struct {
    ID int64 `gorm:"column:id;type:bigint;primaryKey;autoIncrement:false"`
}
```

调用方必须先通过统一组件生成正 ID 并写入模型，再调用 `Create`，不得等待数据库回填主键。GORM 的整数主键可能默认启用自增，必须显式关闭，参见 [GORM 主键自增配置](https://gorm.io/docs/composite_primary_key.html)。`Create(map)` 或跳过钩子的写法也必须提前分配 ID，参见 [GORM 创建行为](https://gorm.io/docs/create.html#Create-From-Map)。

JSON 接口面向 JavaScript 等存在安全整数范围限制的调用方时，雪花 ID 使用十进制字符串传输，不经 `float64` 中转；数据库和 Go 内部仍使用 `BIGINT`、`int64`。参见 [JSON 数值互操作范围](https://www.rfc-editor.org/rfc/rfc8259.html#section-6)。

下面以“禁用指定用户并记录修改时间”为例，说明如何用 `map` 写入零值。`Updates(struct)` 默认跳过 `false`、`0` 和空字符串，而这里的 `false` 正是需要保存的禁用状态。实际业务还应补齐访问与并发条件：

```go
result := db.Model(&UserProfile{}).
    Where("id = ?", userID).
    Updates(map[string]any{
        "is_enabled": false,
        "updated_at": time.Now().UTC().Truncate(time.Millisecond),
    })
```

执行后先检查 `result.Error`，确认是否报错，再按业务检查 `result.RowsAffected`。影响行数为 `0` 时须核对记录是否存在、条件是否匹配或值是否未变化，不能仅凭未报错认定成功。

**模型与 DDL 一致性**

表结构以受版本管理和评审的 SQL 迁移为准，Go 模型必须同步维护。生产环境禁止在应用启动时自动执行 `AutoMigrate`；这是公司的变更管理要求，避免运行时自动推导替代已评审的 DDL。

上线前应核对目标库的 `SHOW CREATE TABLE`，确认字段类型、精度、默认值、主键、唯一约束和 Go 映射一致，且不存在物理外键及 `CHECK` 约束；GORM 标签不等于目标库已经具备相应定义。历史表整改应先确保应用已接管相关校验，再通过受控 SQL 迁移移除这些约束。参见 [GORM 迁移说明](https://gorm.io/docs/migration.html)。

## 3. 索引设计

本章基于 MySQL 8.4、阿里云 RDS 和 InnoDB。主键及业务唯一性遵守 2.3、2.4，本章规定如何选择、组织、验证和维护索引。以下 SQL 为局部示例，完整建表语句在第 4 章给出。

### 3.1 索引设计依据

索引必须对应明确的业务约束或实际查询，不能按字段数量分配，也不能给每个字段各建一个索引。设计时先整理完整 SQL，再确定索引。

每张表的索引设计说明必须包含以下信息：

| 设计依据 | 需要说明的内容 |
| --- | --- |
| 业务约束 | 哪些索引承担主键或业务唯一性，唯一性范围按 2.4 确定 |
| 查询场景 | 完整的过滤、关联、排序、分页、分组和返回字段；包含应用实际添加的租户、软删除等条件 |
| 数据特征 | 当前及预期数据量、主要字段的取值分布、热点值和不同租户的数据量差异 |
| 访问特点 | 调用频率、并发量、读写比例，以及批量任务和低频但必须及时完成的操作 |
| 性能目标 | 预期返回量、响应时间要求及可接受的扫描量，不能只记录“需要走索引” |
| 对应关系 | 每个索引支持哪些 SQL，能否复用已有索引，以及新增索引的必要性 |

具体要求：

- 同时检查查询、更新和删除的定位条件，以及事务中的关联检查、加锁查询。修改少量记录却扫描大量数据，会增加执行时间及锁竞争风险。
- 关联字段按实际访问方向设计索引。例如订单明细经常按 `order_id` 查询时，应检查是否已有以 `order_id` 开头的适用索引；禁止物理外键不代表不需要关联查询索引。
- 布尔值、状态等不同取值较少的字段，不默认单独建索引，也不一律禁止建索引。应结合目标值占比、联合条件、排序和实际收益判断。
- `tenant_id` 只用于存在租户隔离需求的表。租户内查询设计索引时必须纳入租户条件；跨租户任务单独评估，不能要求所有表、所有索引都增加租户列。
- 同一组字段的多个查询应优先评估联合索引复用，不能为每条 SQL 机械增加一个索引。小表或需要读取大部分记录的查询，合理的全表扫描可以接受。

索引的实际选择由优化器根据成本决定，建有索引不保证查询一定使用。参见 [MySQL 索引使用说明](https://dev.mysql.com/doc/refman/8.4/en/mysql-indexes.html)。

### 3.2 索引类型与命名

业务表默认使用 InnoDB 的 B-tree 主键、唯一索引和普通索引。联合索引表示一个索引包含多个键列，覆盖索引表示某个查询所需字段已被索引覆盖，两者都不是需要额外声明的新索引类型。

| 索引类别 | 命名规则 | 使用要求 |
| --- | --- | --- |
| 主键 | MySQL 固定名称 `PRIMARY` | 统一为 `PRIMARY KEY (id)`，雪花主键要求按 2.3 执行 |
| 唯一索引 | `uk_<表名>_<键列名组合>` | 落实 2.4 已确定的业务唯一性，也可以支持查询；不能用普通索引替代其唯一性保障 |
| 普通索引 | `idx_<表名>_<键列名组合>` | 支持过滤、关联、排序等查询，不承担唯一性约束 |
| 全文索引 | `ft_<表名>_<键列名组合>` | 仅在明确采用全文检索方案时设置，不作为默认索引 |

除固定的 `PRIMARY` 外，索引名称使用小写 `snake_case`，实体词使用单数；键列名按索引中的实际顺序排列。名称不得超过 64 个字符，并在同一张表内唯一。名称过长或包含表达式时，保留类别前缀，采用可读的表名缩写和用途短名，并在设计说明中记录完整表名、键列、顺序及表达式，不能依赖 ORM 自动生成不可控的名称。参见 [MySQL 标识符长度限制](https://dev.mysql.com/doc/refman/8.4/en/identifier-length.html)。

以订单号在全表内唯一、同时需要查询用户订单的 `sales_order` 为例，索引定义片段如下：

```sql
PRIMARY KEY (id),
UNIQUE KEY uk_sales_order_order_no (order_no),
KEY idx_sales_order_user_id_payment_status_created_at
    (user_id, payment_status, created_at)
```

其中，唯一索引保证订单号不重复，普通联合索引用于 3.3 的用户订单查询。本组示例不包含租户隔离和软删除；实际模型存在这些要求时，必须补齐相应查询条件并重新验证索引。若业务约定订单号仅在租户内唯一，应按 2.4 改为对应的联合唯一键，不能照搬本例的全表唯一范围。索引不能代替应用的权限和租户隔离检查。

**特殊索引的使用边界**

| 形式或对象 | 使用要求 |
| --- | --- |
| 字符串前缀索引 | 仅在确需缩短较长字符串索引时使用，并验证前缀的区分能力。不能用它代替业务要求的完整字符串唯一键；它也不能完整覆盖原字符串或直接保证完整字符串的排序 |
| 函数索引、生成列索引 | 优先评估能否改写查询以使用普通列索引。确需索引表达式时，明确表达式、结果类型、字符集和比较规则，并验证查询能够匹配该索引 |
| JSON 路径索引 | 稳定且频繁过滤、关联的属性优先设计为普通列。确需索引 JSON 时，明确路径、提取后的类型和缺失值语义，使用适用的生成列或函数索引；不得认为对整个 JSON 值建立普通索引即可查询任意路径。数组多值索引须单独验证适用查询与维护成本 |
| 全文索引 | 明确检索语义、分词方式和语言支持，通过 `MATCH ... AGAINST` 等适用查询验证；不能认为增加全文索引就会加速原有的 `LIKE '%关键词%'` |

字符串索引必须按 `utf8mb4` 的字节需求和实际 InnoDB 限制核对长度，不能把字符数直接当作索引字节数，也不能统一截为某个固定长度来绕过设计。特殊索引的选择理由和验证结果必须随表设计记录。参见 [MySQL 列索引与前缀索引](https://dev.mysql.com/doc/refman/8.4/en/column-indexes.html)、[函数索引说明](https://dev.mysql.com/doc/refman/8.4/en/create-index.html#create-index-functional-key-parts)和 [JSON 索引说明](https://dev.mysql.com/doc/refman/8.4/en/json.html#json-indexing)。

### 3.3 联合索引与查询匹配

**列顺序与过滤条件**

联合索引的键列顺序必须结合查询确定，不能机械采用“区分度最高的列永远放在最前面”。通常先评估共同的等值过滤条件，再结合范围、排序和需要复用该索引的其他查询安排后续列。

以 `(user_id, payment_status, created_at)` 为例：

- 常规定位能力包含 `user_id`、`user_id + payment_status`、`user_id + payment_status + created_at` 这些最左前缀。
- 只有 `payment_status` 或 `created_at` 条件的查询，不能按具备上述前缀定位能力设计。不能依赖优化器偶尔选择的跳跃扫描或全索引扫描来替代必要的索引设计。
- 查询只有 `user_id` 和 `created_at` 条件时，可以先按 `user_id` 定位，但不能当作已有连续的 `(user_id, created_at)` 索引。
- 最左前缀取决于索引定义中的键列顺序，不取决于 SQL 中 `WHERE` 条件的书写先后。
- 使用范围条件后，后续键列能否进一步缩小扫描区间需要结合条件判断；它们仍可能参与索引条件过滤或覆盖查询，不能笼统认定“范围之后的列全部失效”。

多个单列索引不等同于一个适用的联合索引。不能假定优化器一定会合并它们来同时完成过滤和排序。参见 [联合索引](https://dev.mysql.com/doc/refman/8.4/en/multiple-column-indexes.html)和 [范围优化](https://dev.mysql.com/doc/refman/8.4/en/range-optimization.html)。

**排序与分页示例**

下面查询某用户、某支付状态在指定 UTC 时间段内的订单，按创建时间倒序取前 20 条。`?` 为应用参数占位符，两个时间参数分别表示起始时刻和不包含在范围内的结束时刻：

```sql
SELECT id, created_at
FROM order_service.sales_order
WHERE user_id = ?
  AND payment_status = ?
  AND created_at >= ?
  AND created_at < ?
ORDER BY created_at DESC, id DESC
LIMIT 20;
```

3.2 的联合索引先匹配 `user_id`、`payment_status` 的等值条件，再按 `created_at` 扫描时间范围。相同毫秒可能有多条订单，因此排序增加唯一的 `id` 作为第二排序项，避免同时间记录的相对顺序不确定；这不代表按事务提交顺序排序。

InnoDB 普通二级索引包含主键 `id`，本例不必仅为读取 `id` 再显式追加一列。该索引可通过反向扫描满足本例两个排序项均为降序的要求，实际是否采用仍须验证执行计划。混合升降序、跳过中间键列或变更过滤条件时，应重新检查，不能认为字段出现在索引中就一定能消除排序。参见 [二级索引扩展](https://dev.mysql.com/doc/refman/8.4/en/index-extensions.html)和 [ORDER BY 优化](https://dev.mysql.com/doc/refman/8.4/en/order-by-optimization.html)。

连续翻页应优先评估按上一页最后一条记录的 `(created_at, id)` 继续查询，并保留原过滤条件；降序时，后续记录满足 `created_at < 上页时间`，或时间相同且 `id < 上页ID`。不能只用时间作为游标而遗漏同毫秒记录。深度 `OFFSET` 分页仍需扫描并跳过前面的记录，不能认为有索引就没有成本；游标分页也不自动提供跨请求的数据快照。

存在 `GROUP BY`、`DISTINCT` 时，应结合过滤条件、分组或去重字段及聚合方式验证索引收益，不能仅因这些字段都已建索引就认定无需临时表。MySQL 8.4 不保证 `GROUP BY` 结果隐式有序，需要确定顺序时必须显式使用 `ORDER BY`。参见 [GROUP BY 优化](https://dev.mysql.com/doc/refman/8.4/en/group-by-optimization.html)和 [ORDER BY 优化](https://dev.mysql.com/doc/refman/8.4/en/order-by-optimization.html)。

**覆盖查询**

覆盖查询指所需字段均可从所用索引取得，通常可以减少回到聚簇索引读取完整记录的访问。本例只返回 `id`、`created_at`，过滤字段也都在该二级索引中，具备覆盖条件；增加 `payable_amount` 等未包含字段后，需要重新评估。

- 查询显式列出需要的字段，避免默认使用 `SELECT *`。
- 不得为追求覆盖将大量字段、长文本或经常变化的字段追加到索引。
- 覆盖查询是具体 SQL 与索引之间的关系，不能把某个索引永久标记为“覆盖索引”而忽略返回字段变化。

**查询写法要求**

| 场景 | 要求 |
| --- | --- |
| 时间范围 | 优先直接比较时间列，例如 `created_at >= ? AND created_at < ?`；不为筛选某天机械写成 `DATE(created_at) = ?`。按业务时区筛选日期时，由应用先计算相应 UTC 起止时刻 |
| 参数与关联类型 | 按字段类型绑定参数；雪花 ID 使用 `int64`，字符串编号使用字符串。关联列继续遵守 2.3 的类型、字符集和比较规则一致要求，避免隐式转换 |
| 列上的运算 | 普通索引查询中避免对被定位的列套用函数、计算或类型转换；不能改写时，按 3.2 评估匹配的表达式索引 |
| 模糊匹配 | 有固定开头的 `LIKE 'abc%'` 可以具备 B-tree 范围定位条件；`LIKE '%abc%'` 不能依靠该字段的普通 B-tree 前缀范围定位，应另外评估检索方案 |
| 可空列和复杂条件 | `IS NULL` 可以使用索引；`OR`、`IN`、不等值等条件也不能一概认定索引失效，必须结合数据分布和执行计划检查实际扫描范围 |

例如，`VARCHAR` 编号列与数值参数比较，可能既改变匹配结果，又无法按该字符串索引快速定位。参见 [类型转换](https://dev.mysql.com/doc/refman/8.4/en/type-conversion.html)和 [B-tree 索引适用条件](https://dev.mysql.com/doc/refman/8.4/en/index-btree-hash.html)。

### 3.4 索引成本与冗余控制

索引占用存储和缓存；插入、删除及修改索引键值时还需要维护索引。每次新增索引都必须说明查询收益，并评估写入吞吐、响应时间和空间增长。不能仅因“以后可能用到”预建索引，也不能把 MySQL 支持的数量或长度上限当作合理设计目标。

**重复与冗余判断**

| 情况 | 判断与处理要求 |
| --- | --- |
| 两个同类索引的键列、顺序、方向、前缀长度和表达式等定义相同，仅名称不同 | 属于重复索引，应保留一个；同时检查查询中的索引名称引用 |
| 已有唯一索引，又有完全相同键定义的普通索引 | 普通索引通常没有额外价值，应验证后移除，保留唯一性保障 |
| 已有 `(user_id, created_at)`，另有 `(user_id)` 普通索引 | 单列索引是候选冗余，但较窄索引可能仍有收益；结合完整查询集合和实测决定，不直接删除 |
| 已有 `(user_id, created_at)`，另有 `(created_at)` | 不是仅凭包含同一字段就能认定冗余，后者可能服务于独立时间查询 |
| 已有 `UNIQUE(order_no)`，拟用普通索引或 `UNIQUE(order_no, user_id)` 替代 | 不允许按查询覆盖关系直接替代；后两者不能保证原来的订单号唯一性，业务唯一键变更必须重新按 2.4 评审 |
| 为读取主键而给所有普通二级索引追加 `id` | InnoDB 已包含主键，不能机械追加；存在特定排序方向等需求时按实际定义和执行计划判断 |

联合索引只包含实际需要的键列。增加键列或延长字符串索引会增大索引，不能为了覆盖所有 SQL 不断加宽同一个索引；拆分或新增也必须有实际查询依据。

**维护要求**

- 移除索引前检查线上查询、后台任务、报表、数据修复及故障处理场景，覆盖完整业务周期。一次压测或短期使用次数为零，不足以证明索引无用。
- 检查唯一性、列顺序、排序方向、前缀长度和表达式等差异，不能只按字段集合判断索引等价。
- 承担主键、业务唯一性的索引不能仅因查询使用较少而删除。隐藏唯一索引也不会取消其唯一性约束。
- 查询、数据规模或数据分布发生明显变化时，重新验证索引；不得长期保留已无对应场景的索引。

### 3.5 索引验证与变更要求

**变更前：确认查询效果**

新增、调整或删除索引前，先列出受影响的 SQL，并在测试环境比较变更前后的查询结果和执行效率。

测试数据应接近生产环境的数据量和分布。例如，按用户查询订单时，既要测试只有几笔订单的用户，也要测试有大量订单的用户。存在租户隔离或分页需求时，还要测试不同规模的租户和实际使用的分页深度。

先使用 `EXPLAIN` 查看 MySQL 准备怎样执行查询。下面沿用 3.3 的订单查询，检查某用户在 2026 年 11 月 1 日 UTC 全天的已支付订单。示例 ID `10001` 应替换为实际测试值，`20` 沿用前文的已支付状态编码：

```sql
EXPLAIN FORMAT=TRADITIONAL
SELECT id, created_at
FROM order_service.sales_order
WHERE user_id = 10001
  AND payment_status = 20
  AND created_at >= '2026-11-01 00:00:00.000'
  AND created_at < '2026-11-02 00:00:00.000'
ORDER BY created_at DESC, id DESC
LIMIT 20;
```

阅读执行计划时，先看以下字段：

| 字段 | 含义 | 检查重点 |
| --- | --- | --- |
| `key` | 本次查询实际选择的索引 | 是否使用了适合这条 SQL 的索引；`possible_keys` 只是候选索引列表 |
| `type` | 读取记录的方式 | 是按键定位、范围扫描，还是扫描整个索引或整张表 |
| `rows`、`filtered` | 预计检查的行数，以及这些记录中满足条件的比例 | 是否为了返回少量结果而检查大量记录；这里的数值是估算，仍需实测 |
| `Extra` | 执行过程中的补充信息 | 是否可以直接从索引取值，是否需要额外排序或临时表，具体含义见下表 |

需要分析联合索引中哪些键列参与了定位时，再结合 `key_len` 和字段定义检查。`key_len` 表示使用的索引键长度，不能仅凭选中了某个索引，就认定其中所有键列都用于定位。

`Extra` 中常见的四种信息分别表示：

| 内容 | 含义 |
| --- | --- |
| `Using index` | 查询需要的字段都能从当前索引取得，通常不用再读取完整记录，这就是覆盖读取 |
| `Using index condition` | 先用索引中的值排除一部分不符合条件的记录，再读取剩余记录所需的其他字段；这不表示查询已被索引覆盖 |
| `Using filesort` | 需要额外执行排序，可能在内存中完成，也可能使用磁盘 |
| `Using temporary` | MySQL 使用内部临时表保存查询的中间结果，常见于分组、去重等操作；临时表可能位于内存或磁盘 |

例如，上面的订单查询只返回 `id`、`created_at`，过滤字段也在 3.2 的联合索引中，因此具备覆盖读取的条件。若实际选择了该索引，应进一步检查是否利用索引顺序取出了前 20 条记录，以及是否还有额外排序。

额外排序和临时表是否需要优化，要看处理的数据量和实际耗时。例如，只排序几十条结果，与排序几百万条结果的成本不同。不能仅凭 `Extra` 中出现某个词就判定查询通过或失败。参见 [执行计划字段说明](https://dev.mysql.com/doc/refman/8.4/en/explain-output.html)和 [排序执行方式](https://dev.mysql.com/doc/refman/8.4/en/order-by-optimization.html)。

看完计划后，还必须实际执行测试查询，比较变更前后的耗时、扫描量和返回结果。索引被选中，并不等于查询已经变快；新增索引还应测试写入性能，确认维护索引的开销可以接受。

需要查看实际行数和执行耗时时，可以在测试环境对无写入副作用的 `SELECT` 使用 `EXPLAIN ANALYZE`。它会真实执行语句，也支持部分修改语句，因此不能当作普通的计划预览。生产排查先使用普通 `EXPLAIN`。参见 [EXPLAIN 语句说明](https://dev.mysql.com/doc/refman/8.4/en/explain.html)。

如果计划估算与实测差距很大，先检查查询条件、数据分布和统计信息，再决定是否需要调整索引。需要通过 `ANALYZE TABLE` 更新统计信息时，也应安排执行时机，因为它会消耗资源，并可能改变后续查询计划。不能直接给所有查询添加 `FORCE INDEX` 来代替原因分析。

**执行变更：安排方式、时间和恢复方案**

索引变更按 2.6 使用受版本管理和评审的 SQL 迁移。迁移记录应写清目标实例和库表、变更 SQL、测试结果、执行时间及恢复步骤，生产应用启动时不得自动创建索引。

执行前落实以下事项：

- **新增唯一索引**：先按目标字段、比较规则和规范化要求检查历史重复数据，并按业务规则修复。还要安排变更期间的写入控制，避免继续产生重复数据。检查后仍可能发生并发冲突；遇到重复键错误时，应查明并处理原因，不能直接丢弃冲突记录。
- **确定 DDL 执行方式**：根据实际 RDS 内核和操作类型核对支持范围。普通二级索引的新增、删除通常支持 `ALGORITHM=INPLACE, LOCK=NONE`；其他索引和组合变更须分别核对。不支持预定方式时，重新安排执行方式和时间。
- **控制阻塞和资源消耗**：`LOCK=NONE` 允许索引构建期间并发读写，但修改表定义时仍需要元数据锁，长事务可能使 DDL 等待。建索引还需要读取数据和写入索引，因此执行前应检查长事务、CPU、I/O、剩余空间和复制延迟，明确最长等待时间，以及出现业务延迟或资源异常时的中止步骤。
- **删除普通索引**：可以先将其设为不可见，观察日常查询和相关定时任务是否受影响。默认情况下优化器不再使用它，可据此检查查询是否变慢。若应用使用了索引名称提示或允许使用不可见索引的设置，应单独核对。不可见索引仍被维护，因此这一步只能观察查询影响，不能测试真正删除后的写入收益。

恢复方案必须写出具体操作。不可见索引可以恢复为可见；已经删除的索引通常需要重新构建，应预留重建时间和资源。主键不能设为不可见，唯一索引的删除仍须遵守 2.4、3.4，不能按普通索引直接处理。参见 [Online DDL 支持范围](https://dev.mysql.com/doc/refman/8.4/en/innodb-online-ddl-operations.html)、[Online DDL 的锁与并发影响](https://dev.mysql.com/doc/refman/8.4/en/innodb-online-ddl-performance.html)和 [不可见索引](https://dev.mysql.com/doc/refman/8.4/en/invisible-indexes.html)。

使用 RDS 非阻塞 DDL、DDL 限速等功能时，先核对实例内核是否支持、相关参数是否已启用。使用 DMS 时，还要核对工具是否支持本次操作，尤其不能直接套用“无锁结构变更”来新增唯一键。相关限制参见 [RDS 非阻塞 DDL](https://help.aliyun.com/zh/rds/apsaradb-rds-for-mysql/non-blocking-ddl)、[RDS DDL 限速](https://help.aliyun.com/zh/rds/apsaradb-rds-for-mysql/ddl-throttling)和 [DMS 支持范围](https://help.aliyun.com/zh/dms/lock-free-structure-change/)。

**变更后：核对结构和业务表现**

DDL 执行成功后，先核对实际表结构。以下语句逐条执行：

```sql
SHOW CREATE TABLE order_service.sales_order;
SHOW INDEX FROM order_service.sales_order;
```

检查索引名称、唯一性、键列顺序、排序方向、前缀长度、表达式和可见性是否与迁移 SQL 一致。

随后重新执行受影响的关键 SQL，核对结果、执行计划和耗时。上线后再结合 RDS 慢查询、应用请求延迟和写入吞吐观察实际表现，并按执行前确定的资源指标继续监控。确认结构正确、查询耗时达到目标，写入性能和资源占用也在约定范围内后，完成本次变更验收。

## 4. 完整示例与评审清单

### 4.1 示例中的数据与关系

本例是一套会员社区。用户可以关注其他用户、发布帖子和点赞，也可以购买会员。先看这些业务需要保存哪些数据，再看它们怎样关联和分库。

#### 4.1.1 七张表分别保存什么

| 业务数据 | 表名 | 每行保存什么 |
| --- | --- | --- |
| 用户资料 | `user_profile` | 一位用户的身份、昵称、头像和启用状态 |
| 用户关注 | `user_follow` | 一位用户对另一位用户的一条当前关注关系 |
| 帖子 | `post` | 一篇帖子的作者、标题、正文和删除状态 |
| 帖子点赞 | `post_like` | 一位用户对一篇帖子的一条当前点赞关系 |
| 会员订单 | `membership_order` | 一次会员购买的规格、金额和支付结果 |
| 当前会员权益 | `user_membership` | 一位用户当前的会员等级、生效时间和到期时间 |
| 权益变更历史 | `membership_change_record` | 一次开通或续费前后，会员权益发生的变化 |

关注和点赞表只保留用户尚未取消的关系。会员权益表保存当前状态，变更历史表保存每次变化，两者承担不同职责。

#### 4.1.2 这些数据怎样关联

**用户与社交关系**：用户既可以发起关注，也可以被其他用户关注。一条关注关系连接两位用户，并区分方向；A 关注 B 和 B 关注 A 是两条不同关系。

**用户、帖子与点赞**：用户发布帖子，帖子记录作者。另一位用户点赞时，点赞记录连接这位用户和这篇帖子。帖子另外保存点赞数，便于列表展示；用户取消点赞后，当前点赞记录删除，计数随之减少。

**订单、当前权益与变更历史**：购买会员先产生订单。确认支付后，更新该用户的当前权益，同时追加一条变更历史。每位用户最多一份当前权益，首次购买前没有会员记录，首次开通时创建，后续续费更新同一份当前权益。

例如，用户先成功开通 30 天会员，再续费 30 天，订单表和变更历史表各增加两条记录；当前权益表保留一条记录，更新为续费后的到期时间。

#### 4.1.3 这些表分别属于哪个库

| 业务库 | 所属数据表 |
| --- | --- |
| `user_service` | `user_profile`、`user_follow`、`user_membership`、`membership_change_record` |
| `post_service` | `post`、`post_like` |
| `order_service` | `membership_order` |

三个库位于同一应用、同一环境的 RDS MySQL 8.4 主实例。普通业务操作各自的库；用户服务提供作者资料，再由应用与帖子数据组装。只有已授权的支付确认模块需要同时修改订单库和用户库，回调与支付核对任务共用这一模块。

表间通过对象标识关联，由应用维护这些关系，数据库不创建物理外键。

本章采用单租户模型。完整结构以 4.2 的 DDL 为准；前文的局部字段、模型片段和其他示意表用于说明单项规则，三元关系、价格有效版本等内容继续按前文示例理解。

本例的支付渠道在下单时确定，尚未取得渠道流水时使用 SQL `NULL`。联合唯一键允许同渠道的多笔未取得流水订单；取得非空流水后，约束同一渠道流水只能关联一笔订单。应用不得用空字符串代替未知流水，且在将订单置为已支付且已完成权益发放前，必须校验并填写渠道流水、实际支付时间与本地履约处理时间。渠道与固定商户账户的对应关系属于本例前提，扩大商户账户范围时必须重新设计流水唯一性范围。

所有字符列继承所在表的字符集和比较规则；有符号 `BIGINT` 在 Go 中映射为 `int64`，`INT` 映射为 `int32` 或对应底层类型的业务枚举，`is_enabled` 映射为 `bool`；可空字符串使用 `sql.NullString`，可空时间使用 `sql.NullTime`，变更前可空等级使用 `sql.NullInt32`。所有时间写入仍遵守 UTC 及毫秒精度要求。

### 4.3 关键写入流程

以下按业务操作说明读写哪些数据，并给出参数化 SQL 片段。实际执行时必须遵守 4.5 的统一发号、鉴权、请求幂等和事务约定；SQL 中的 `?` 由应用绑定参数，互斥分支只执行符合条件的一支。

#### 4.3.1 注册用户与修改资料

本例中，一个已验证的外部账户对应一位用户，昵称只是展示名称，允许重名；不演示多个外部身份的绑定或合并。账户来源与标识取自认证组件的核验结果，`account_source` 与 `external_account_id` 在注册后不由普通资料编辑接口修改。

`account_source` 是服务端配置的身份命名空间代码，完整区分来源系统、租户及应用等标识范围，不能只用一个可能混淆身份的宽泛平台名称。本例代码最多 32 个字符，来源内账户标识最多 128 个字符，由接入来源的契约保证；外部标识按原字符串保存，不自动转整数、改大小写或截断。

先在公共幂等事务中按账户身份查找用户：

```sql
SELECT id, is_enabled
FROM user_service.user_profile
WHERE account_source = ?
  AND external_account_id = ?;
```

已有用户时返回该用户，不覆盖原昵称、头像，也不自动启用已停用账户。不存在时才生成新用户 ID 并插入；`is_enabled`、`version` 使用已确定的初始默认值。头像未提供时写 SQL `NULL`，提供时检查格式和长度。

```sql
INSERT INTO user_service.user_profile (
    id, account_source, external_account_id,
    user_name, avatar_url, created_at, updated_at
) VALUES (?, ?, ?, ?, ?, ?, ?);
```

并发注册同一外部账户时，由联合唯一键兜底。遇到该身份的唯一冲突后回滚整个事务，再以原请求标识重新进入幂等流程，核对并返回已有用户、保存本次回执，不能将任意主键冲突都当作账户已存在。重复同次请求返回原结果；即使使用新的请求标识，也不能为同一外部账户创建第二个用户。

资料修改携带调用方读取到的旧版本：

```sql
UPDATE user_service.user_profile
SET user_name = ?,
    avatar_url = ?,
    updated_at = ?,
    version = version + 1
WHERE id = ?
  AND version = ?
  AND is_enabled = 1;
```

本次更新必须影响一行；为零时检查用户是否存在、是否停用或版本是否已变化。所有资料修改入口，包括后台启用、停用用户，都要遵守版本维护规则；启用、停用入口的授权条件另行校验，不能复用仅允许启用用户编辑的上述条件。

本例只演示用户启用和停用，不演示注销或物理清理。停用用户不能通过鉴权入口发起新的业务操作，但保留旧帖子、关注、点赞和订单，也不暂停会员期限。已经在渠道付款的订单仍按 4.3.5 完成履约，不会因支付成功自动重新启用用户。

#### 4.3.2 关注与取消关注

关注是有方向的关系：`follower_user_id` 是当前调用用户，`followed_user_id` 是目标用户。应用先拒绝自关注，然后在公共幂等入口中执行：

1. 开启事务，将两个用户 ID 排序，先锁定较小 ID 的用户，再锁定较大 ID 的用户。下面的锁定 SQL 分别执行两次，不按请求中参数的先后顺序加锁。
2. 确认两个用户存在。建立关注时双方都必须启用；取消关注时，调用用户必须启用，被关注用户停用不妨碍解除原关系。
3. 查询当前关系，按建立或解除操作执行一个分支。
4. 保存幂等回执并提交事务。本例不保存冗余关注数，查询时按关系统计。

锁定用户和查询关系的 SQL：

```sql
SELECT id, is_enabled
FROM user_service.user_profile
WHERE id = ?
FOR UPDATE;

SELECT id
FROM user_service.user_follow
WHERE follower_user_id = ?
  AND followed_user_id = ?
FOR UPDATE;
```

- **建立关注**：已存在关系则按当前关系已建立处理；不存在时分配新 ID，并执行插入。
- **取消关注**：没有关系则按已解除处理；存在时按查询到的关系 ID 删除，必须影响一行。

```sql
-- 建立分支
INSERT INTO user_service.user_follow (
    id, follower_user_id, followed_user_id, created_at
) VALUES (?, ?, ?, ?);

-- 解除分支
DELETE FROM user_service.user_follow
WHERE id = ?
  AND follower_user_id = ?
  AND followed_user_id = ?;
```

再次主动关注会生成新的关系 ID 和建立时间。同一次旧请求的重试由公共幂等组件拦截，不能因原关系已经删除就重新执行插入。

#### 4.3.3 发帖、点赞与取消点赞

**发布帖子**

作者标识取自服务端认证结果，标题和正文由应用检查非空及容量。正文须满足 `TEXT` 的字节容量，不能只按 Go 字符串的字符数量判断。发布后即为本例可见帖子，不增加草稿或审核状态。

```sql
INSERT INTO post_service.post (
    id, author_user_id, title, content, created_at, updated_at
) VALUES (?, ?, ?, ?, ?, ?);
```

新帖的 `like_count` 默认为 `0`，`deleted_at` 默认为 `NULL`。发帖也通过公共幂等入口执行。

**点赞与取消点赞**

两个操作均在事务中先锁定帖子，再检查当前关系：

```sql
SELECT id, author_user_id, deleted_at, like_count
FROM post_service.post
WHERE id = ?
FOR UPDATE;

SELECT id
FROM post_service.post_like
WHERE post_id = ?
  AND user_id = ?
FOR UPDATE;
```

帖子不存在或已软删除时拒绝互动。点赞用户来自当前认证身份；不读取或修改其他业务库的用户表来代替鉴权。

- **点赞**：关系已存在时不修改计数；不存在时新建关系，再将计数加一。
- **取消点赞**：关系不存在时不修改计数；存在时先检查计数大于零，再删除关系并将计数减一。关系存在但计数为零是数据不一致，回滚并进入核对流程。

点赞分支的两条 SQL 在同一个事务中执行，均须影响一行：

```sql
INSERT INTO post_service.post_like (
    id, post_id, user_id, created_at
) VALUES (?, ?, ?, ?);

UPDATE post_service.post
SET like_count = like_count + 1,
    updated_at = ?
WHERE id = ?
  AND deleted_at IS NULL;
```

取消分支的两条 SQL 也在同一个事务中执行，均须影响一行：

```sql
DELETE FROM post_service.post_like
WHERE id = ?
  AND post_id = ?
  AND user_id = ?;

UPDATE post_service.post
SET like_count = like_count - 1,
    updated_at = ?
WHERE id = ?
  AND deleted_at IS NULL
  AND like_count > 0;
```

计数更新失败时，前面的关系新增或删除必须一起回滚。不得把每次请求都当成一次计数变化，也不通过 `GREATEST(0, ...)` 隐藏计数错误。

所有建立、解除关系及计数修复入口都先锁定同一帖子。这样即使隔离级别是 `READ COMMITTED`，也能通过共同的帖子锁串行处理该帖的关系变化。锁必须持有到事务结束，参见 [MySQL 锁定读](https://dev.mysql.com/doc/refman/8.4/en/innodb-locking-reads.html)。

#### 4.3.4 帖子软删除、恢复与计数修复

帖子采用软删除：隐藏帖子，保留点赞关系和计数，供以后恢复。删除期间不接受编辑、点赞和取消点赞。本例只允许作者删除和恢复自己的帖子。两个入口也使用公共幂等组件，回执与状态变化同事务提交；已完成的旧删除或恢复请求不能在后续状态变化后重新执行。应用在事务中先按 4.3.3 锁定帖子，核对作者身份，再处理对应分支：

| 操作 | 处理规则 |
| --- | --- |
| 删除未删除的帖子 | 写入 UTC 删除时间；保留全部尚未取消的点赞和计数 |
| 重复删除 | 返回已删除结果，不重写第一次删除时间 |
| 恢复已删除帖子 | 按保留的点赞关系核对计数，解除帖子删除标记 |
| 重复恢复 | 返回当前已恢复结果，不重新建立任何点赞关系 |

```sql
-- 删除分支
UPDATE post_service.post
SET deleted_at = ?,
    updated_at = ?
WHERE id = ?
  AND deleted_at IS NULL;

-- 恢复分支：先统计保留关系，再把统计结果与恢复状态一起写回
SELECT COUNT(*) AS actual_like_count
FROM post_service.post_like
WHERE post_id = ?;

UPDATE post_service.post
SET deleted_at = NULL,
    like_count = ?,
    updated_at = ?
WHERE id = ?
  AND deleted_at IS NOT NULL;
```

实际删除、恢复分支的更新必须影响一行。业务可见性变化与恢复时的计数修正一起提交，普通查询始终过滤 `post.deleted_at IS NULL`。整个流程不修改点赞记录，因此用户此前已取消的点赞不会被恢复。

后台修复计数也使用相同帖子锁：在同一个事务中锁定帖子、按 `post_id` 统计关系，仅在计数不一致时更新 `like_count` 和 `updated_at`。批量巡检按帖子分成短事务，不能先在事务外统计，再无条件写回旧结果。

#### 4.3.5 创建会员订单与支付回调

**本例购买规则**

用户购买的是标准会员资格，一笔订单购买一期。每期固定为 30×24 小时；首次开通从本地确认履约的处理时刻起生效，未到期续费从原到期时间继续延长，已到期续费从本次处理时刻重新起算。过期会员记录保留，后续购买仍更新这份当前权益。

本例服务端套餐配置如下，订单保存购买时的这份配置：

| 配置项 | 示例值 |
| --- | --- |
| 套餐编码 `plan_code` | `standard_30_day` |
| 套餐版本 `plan_version` | `1` |
| 会员等级 `membership_level` | `10`，标准会员 |
| 时长 `duration_seconds` | `2592000` 秒，即 30×24 小时 |
| 应付金额 `payable_amount` | `2900` 分，即 29 元 |
| 币种 `currency_code` | `CNY` |

上表的套餐来自可信的、带版本的服务端配置，不接受客户端提交的价格或时长作为定价依据。订单保存下单时的配置快照；后续配置调整不改变已创建订单的购买内容。

一笔订单只接受一次成功支付，并产生一条只追加、不修改、不软删除的权益变更历史。订单状态 `10` 表示待支付，`20` 表示已确认支付且已完成权益发放。订单关闭、退款、支付尝试历史和等级升级折算不在本例中展开。

**创建订单**

应用根据认证用户、选择的套餐编码和支付渠道读取可信配置，生成雪花 ID 与独立业务订单号，保存购买快照。会员记录尚不存在不影响下单。

```sql
INSERT INTO order_service.membership_order (
    id, order_no, user_id,
    plan_code, plan_version, membership_level, duration_seconds,
    payable_amount, currency_code, payment_channel,
    created_at, updated_at
) VALUES (?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?);
```

创建时 `payment_status=10`，渠道流水、支付时间和履约时间均为 SQL `NULL`。金额、期限和等级不得从客户端提交值直接入库；本例必须与本节的服务端套餐配置一致。

订单提交后，才使用该订单号和快照请求支付渠道。网络请求在数据库事务外进行；请求失败或结果未知时，保留原订单，按原订单号重试或查询渠道结果，不重新创建业务订单。本例不记录每次渠道调用尝试。

**核验支付并执行受控事务**

签名校验、必要的渠道查询在加锁前完成，得到经核验的商户身份、订单号、渠道交易号、金额、币种和支付成功时间。本例将渠道金额精确转换为 CNY 分后与 `payable_amount` 比较，不经浮点数中转。受益用户始终从本地订单读取，不采用回调新传入的用户标识。

通过专用连接开启一个 `sql.Tx`，依次处理：

1. 按订单号锁定订单，重新核对渠道、固定商户账户、金额和币种。订单不存在、状态未知或核验不符时停止处理，不新建订单承接未知支付。成功流水必须非空，`paid_at` 使用渠道实际支付时间并转换为 UTC 毫秒精度。
2. 若订单已为 `20`，核对原渠道流水和该订单的权益变更记录。确认同一次支付已经完成后返回既有结果，不再次延长权益；发现不同流水或历史缺失时作为异常处理。
3. 若订单为 `10`，按订单中的 `user_id` 锁定真实存在的用户，再查询并锁定已有会员记录。用户停用不取消已成功支付的履约，也不得在回调中自动启用用户。
4. 获取本次 UTC 毫秒处理时刻 `t`，按下表计算权益，校验等级、期限、时间范围及运算溢出。
5. 新建或更新当前会员记录，追加本订单的权益变更历史，将订单改为 `20` 并填写支付与履约信息。
6. 三项写入全部成功后统一提交，才确认回调处理成功。任一步失败显式回滚整个事务。

锁定顺序和查询 SQL 如下：

```sql
SELECT id, order_no, user_id,
       plan_code, plan_version, membership_level, duration_seconds,
       payable_amount, currency_code, payment_channel,
       payment_status, payment_transaction_no, paid_at, fulfilled_at
FROM order_service.membership_order
WHERE order_no = ?
FOR UPDATE;

SELECT id, is_enabled
FROM user_service.user_profile
WHERE id = ?
FOR UPDATE;

SELECT id, membership_level, effective_at, expired_at
FROM user_service.user_membership
WHERE user_id = ?
FOR UPDATE;
```

订单已支付时核对的历史记录：

```sql
SELECT id, user_id, membership_id, order_id, change_type,
       after_membership_level, after_effective_at, after_expired_at
FROM user_service.membership_change_record
WHERE order_id = ?;
```

同一用户的所有权益创建、续费入口都必须先锁用户行。不能只锁尚不存在的会员记录，随后假定并发首购已经被阻止。事务账号还须具备实际锁定读所需权限，不能只授予普通查询权限而忽略 `FOR UPDATE` 的授权要求。

| 当前权益 | 本次处理 |
| --- | --- |
| 无会员记录 | 类型为 `10` 开通；新生效时间为 `t`，新到期时间为 `t + 订单快照时长`；变更前的等级和两个时间均为 SQL `NULL` |
| 同级且未到期 | 类型为 `20` 续费；保留原生效时间，新到期时间为 `原到期时间 + 订单快照时长` |
| 同级且已到期 | 类型为 `20` 续费；新生效时间为 `t`，新到期时间为 `t + 订单快照时长` |

统一的到期计算为：`new_expired_at = max(t, before_expired_at) + duration_seconds`；首购时基准为 `t`。未来生效、未知等级或不同等级等不符合本例规则的数据应作为异常处理，不能直接覆盖等级。应用先校验时长和计算范围，再做时间运算，不能无检查地将任意 `BIGINT` 秒数转换成 Go `time.Duration`。

当前权益只执行下列一个分支；首购时生成新的会员记录 ID，续费沿用当前会员记录 ID：

```sql
-- 首次开通分支
INSERT INTO user_service.user_membership (
    id, user_id, membership_level,
    effective_at, expired_at, created_at, updated_at
) VALUES (?, ?, ?, ?, ?, ?, ?);

-- 续费分支
UPDATE user_service.user_membership
SET membership_level = ?,
    effective_at = ?,
    expired_at = ?,
    updated_at = ?
WHERE id = ?
  AND user_id = ?;
```

随后插入变更记录，并更新订单，两条 SQL 与上面的当前权益写入使用同一个事务：

```sql
INSERT INTO user_service.membership_change_record (
    id, user_id, membership_id, order_id, change_type,
    before_membership_level, before_effective_at, before_expired_at,
    after_membership_level, after_effective_at, after_expired_at,
    created_at
) VALUES (?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?);

UPDATE order_service.membership_order
SET payment_status = 20,
    payment_transaction_no = ?,
    paid_at = ?,
    fulfilled_at = ?,
    updated_at = ?
WHERE id = ?
  AND payment_status = 10
  AND payment_channel = ?;
```

每笔成功履约的会员写入、历史插入和订单条件更新均必须影响一行。`UNIQUE(order_id)` 防止同单重复历史；渠道与流水的唯一键防止同一笔成功支付用于不同订单。任何重复键错误都回滚本次完整事务，核对后再决定返回结果，不吞错继续提交。

例如，按上述固定时长计算，以下时间均为 UTC：

| 操作 | 处理时刻 | 原到期时间 | 新到期时间 |
| --- | --- | --- | --- |
| 首次开通 | 2026-11-02 02:00:00.000 | 无 | 2026-12-02 02:00:00.000 |
| 未到期续费 | 2026-11-12 02:00:00.000 | 2026-12-02 02:00:00.000 | 2027-01-01 02:00:00.000 |
| 重复通知第一笔订单 | 任意后续处理时刻 | 当前权益可能已被第二笔订单延长 | 不变，不再次增加 30 天 |

重复回调核对的是原订单与对应历史，而不是要求当前权益仍等于那笔历史的变更后值。后续续费可以合法改变当前权益。会员是否已到期由查询时刻判断，不靠后台把会员行删除或将等级改成零。

**未收到回调时核对支付结果**

定时任务在订单库按创建时间分段、分页读取仍待支付的订单，再到渠道查询结果。渠道确认支付成功时，调用上面同一个受控支付确认模块；确认仍未支付时保留待支付状态，不由核对任务绕过权益流程直接修改订单状态。

```sql
SELECT id, order_no, payment_channel, created_at
FROM order_service.membership_order
WHERE payment_status = 10
  AND created_at >= ?
  AND created_at < ?
ORDER BY created_at ASC, id ASC
LIMIT 100;
```

继续分页使用对应的 `created_at + id` 升序游标。每轮核对必须覆盖仍未确认的旧订单，不能永久跳过此前查到未支付的订单；调用频率按渠道限流和履约恢复要求确定。网络查询仍放在事务外，所有本地履约都复用同一订单幂等和锁定流程。

### 4.4 关键查询、索引与数据核对

#### 4.4.1 查询当前会员权益

```sql
SELECT id, user_id, membership_level, effective_at, expired_at
FROM user_service.user_membership
WHERE user_id = ?;
```

没有记录表示尚未开通；有记录时，应用以同一次 UTC 查询时刻判断 `effective_at <= t AND t < expired_at`。到期不删除记录，新的购买仍按 4.3.5 续费规则处理。

#### 4.4.2 查询关注列表和粉丝列表

以下列表只展示当前启用的对端用户，用户停用不等同于解除关注。当前调用用户身份由鉴权入口确认。

```sql
-- 我的关注
SELECT f.id AS follow_id,
       u.id AS followed_user_id,
       u.user_name,
       f.created_at AS followed_at
FROM user_service.user_follow AS f
JOIN user_service.user_profile AS u ON u.id = f.followed_user_id
WHERE f.follower_user_id = ?
  AND u.is_enabled = 1
ORDER BY f.created_at DESC, f.id DESC
LIMIT 20;

-- 我的粉丝
SELECT f.id AS follow_id,
       u.id AS follower_user_id,
       u.user_name,
       f.created_at AS followed_at
FROM user_service.user_follow AS f
JOIN user_service.user_profile AS u ON u.id = f.follower_user_id
WHERE f.followed_user_id = ?
  AND u.is_enabled = 1
ORDER BY f.created_at DESC, f.id DESC
LIMIT 20;
```

两个方向分别使用以 `follower_user_id`、`followed_user_id` 开头的列表索引。组合唯一索引负责防止重复关注，不能仅因其首列相同就认定列表排序索引无用。

#### 4.4.3 查询帖子和用户点赞列表

全站帖子列表不读取大正文：

```sql
SELECT id, author_user_id, title, like_count, created_at
FROM post_service.post
WHERE deleted_at IS NULL
ORDER BY created_at DESC, id DESC
LIMIT 20;
```

作者帖子列表增加明确的作者条件，使用相应联合索引：

```sql
SELECT id, author_user_id, title, like_count, created_at
FROM post_service.post
WHERE author_user_id = ?
  AND deleted_at IS NULL
ORDER BY created_at DESC, id DESC
LIMIT 20;
```

“我点赞的帖子”表示用户尚未取消点赞、且帖子目前未删除的结果：

```sql
SELECT l.id AS like_id,
       p.id AS post_id,
       p.title,
       p.like_count,
       l.created_at AS liked_at
FROM post_service.post_like AS l
JOIN post_service.post AS p ON p.id = l.post_id
WHERE l.user_id = ?
  AND p.deleted_at IS NULL
ORDER BY l.created_at DESC, l.id DESC
LIMIT 20;
```

`post_like` 不使用软删除，因此不添加 `l.deleted_at`。在同一条 SQL 中关联、过滤和分页，不能先取一页点赞记录再由应用过滤已删除帖子。

上述 SQL 是第一页。继续读取点赞列表时，在原 `WHERE` 条件中增加以下游标条件，参数来自上一页最后一条结果的 `liked_at`、`like_id`：

```sql
AND (
    l.created_at < ?
    OR (l.created_at = ? AND l.id < ?)
)
```

前两个时间参数传相同值，保留原排序和 `LIMIT`。关注、帖子、订单和权益历史列表也使用各自记录的 `created_at + id` 作为游标。接口中的雪花 ID 按 2.6 使用十进制字符串，不能经过浮点数转换。

列表总数采用与列表相同的关联、权限和状态条件。例如可见点赞帖子的数量：

```sql
SELECT COUNT(*) AS visible_post_count
FROM post_service.post_like AS l
JOIN post_service.post AS p ON p.id = l.post_id
WHERE l.user_id = ?
  AND p.deleted_at IS NULL;
```

这些是实时列表，跨页和分开执行的总数查询不承诺固定快照。某用户有大量点赞指向已删除帖子时，返回 20 条结果可能需要检查更多点赞；必须用代表性数据验证，不能把 `LIMIT 20` 理解为只访问 20 行。

#### 4.4.4 查询订单和权益变更历史

```sql
SELECT id, order_no, membership_level, duration_seconds,
       payable_amount, currency_code, payment_status,
       paid_at, fulfilled_at, created_at
FROM order_service.membership_order
WHERE user_id = ?
ORDER BY created_at DESC, id DESC
LIMIT 20;

SELECT id, order_id, change_type,
       before_membership_level, before_effective_at, before_expired_at,
       after_membership_level, after_effective_at, after_expired_at,
       created_at
FROM user_service.membership_change_record
WHERE user_id = ?
ORDER BY created_at DESC, id DESC
LIMIT 20;
```

订单展示购买内容及支付履约结果，历史展示每次权益变化，两者不互相覆盖。用户服务需要展示订单号等信息时，通过订单服务按授权提供，不自行进行跨库 JOIN。

#### 4.4.5 核对点赞数与索引效果

以下查询核对单篇帖子，包含被软删除但仍保留关系的帖子：

```sql
SELECT p.id,
       p.like_count,
       COUNT(l.id) AS actual_like_count
FROM post_service.post AS p
LEFT JOIN post_service.post_like AS l ON l.post_id = p.id
WHERE p.id = ?
GROUP BY p.id, p.like_count;
```

没有点赞时 `COUNT(l.id)` 为零；不能改成 `COUNT(*)`，否则 LEFT JOIN 产生的空匹配行也会被计入。没有帖子时返回空结果，不等于帖子点赞数为零。发现差异后按 4.3.4 的锁定和修复流程处理。

各索引的验证目标如下；具体计划按第 3 章在实际规模的数据上检查：

| 索引 | 支持的操作 |
| --- | --- |
| `user_profile` 的账户身份联合唯一索引 | 注册或登录时定位固定账户对应的用户，防止同一外部身份重复注册 |
| `user_membership` 的 `UNIQUE(user_id)` | 定位当前权益，并保证每用户至多一条 |
| `user_follow` 的组合唯一索引 | 识别当前关注关系，防止重复建立 |
| `user_follow` 两个方向的列表索引 | 按建立时间查询关注或粉丝 |
| `post` 的作者与删除时间联合索引 | 查询某作者的可见帖子列表 |
| `post` 的删除时间与创建时间联合索引 | 查询全站可见帖子列表 |
| `post_like` 的组合唯一索引 | 识别当前点赞、按帖子统计和清理关系 |
| `post_like` 的用户列表索引 | 按点赞时间取用户列表，并从索引取得关联帖子 ID |
| `membership_order` 的两个唯一索引 | 定位订单、防止业务订单号及渠道成功支付重复 |
| `membership_order` 与 `membership_change_record` 的用户列表索引 | 查询订单和权益变化的时间顺序 |
| `membership_order` 的支付状态与创建时间索引 | 分段查询待支付订单，核对丢失回调或结果未知的支付 |
| `membership_change_record` 的 `UNIQUE(order_id)` | 定位某次履约结果，防止同单重复历史 |

### 4.5 执行约定与公共能力

本节汇总业务 SQL 落地时的共同要求，与前面的各条流程一起执行。

#### 4.5.1 SQL 与事务执行约定

1. `?` 是 Go 驱动参数占位符，各参数由应用校验后绑定；本章 SQL 块不是可以一次发送的多语句请求，连接仍保持 `multiStatements=false`。
2. 一个业务事务内的查询、加锁和写入全部使用同一个 `sql.Tx`，由应用调用 `Commit` 或 `Rollback`。SQL 块中的互斥分支只执行符合条件的一支。
3. ID 在创建前通过统一组件分配；同次创建重试复用已分配 ID，新业务操作生成新 ID。
4. 时间由应用转换为 UTC 并截断到毫秒。一笔写入使用明确的处理时刻 `t`；渠道支付时间另行解析，不能用处理时间冒充支付时间。
5. 任一业务检查或 SQL 失败，显式回滚整个事务。实际新增、删除及条件更新按对应流程检查影响行数；幂等空操作单独处理，不盲目执行后续计数。
6. 死锁、锁等待超时和重复键错误按事务边界处理；重试前核对业务幂等结果。提交报错时结果可能未知，先在主实例核对订单或原请求结果，不能直接换新 ID 重做。参见 [InnoDB 错误处理](https://dev.mysql.com/doc/refman/8.4/en/innodb-error-handling.html)。

#### 4.5.2 公共组件与请求幂等

本章各写入流程均先完成身份、权限及参数校验，再进入业务事务。普通服务不得为了校验用户而自行获取跨库写权限；跨服务用户状态由鉴权或用户服务提供，本例不实现用户停用状态的跨服务即时撤销协议。

本例要求应用提供统一发号、认证鉴权、时间处理和持久化请求幂等能力。七张表是业务表清单，不包含这些公共组件的技术表或实现。公共幂等组件在各服务自己的库内保存技术回执，复用当前事务；实现统一不等于把回执集中写入另一个库。

本例用户发起的写入，包括注册、资料修改、关注、发帖、点赞、删帖、恢复和创建订单，都通过公共幂等入口执行。幂等组件必须满足以下契约：

- 请求携带稳定的 `request_id`，按调用者、操作类型和请求标识识别一次操作，并核对目标资源及参数；同一标识携带不同内容时拒绝执行。注册调用者使用已验证的外部账户身份识别，其他用户操作使用内部用户 ID。
- 请求处理结果持久化，且可与业务写入使用同一个 `sql.Tx` 原子提交。已完成请求重试时返回原操作回执，不重新执行写入；回执不是当前业务状态，当前状态通过查询取得。
- 明确回执保留窗口；窗口之外的旧请求不得直接当作新请求执行。当前关系的组合唯一键、进程内记录或临时缓存锁都不能替代这项能力。
- 本例要求客户端对同一关系顺序提交操作，前一次结果确认后再提交新的建立或解除操作；超时先用原请求标识核对或重试，不更换标识绕过未确认结果。不同请求的业务顺序不能只靠去重保证；需要处理乱序命令的应用，应另行设计命令序号或版本校验。

4.3 展示业务写入部分。公共幂等组件的建表与实现不在本章中；未接入满足上述契约的组件，不能宣称七张业务表本身已经防住“取消后重放旧点赞请求”。幂等与迟到请求的背景可参见 [AWS 幂等接口设计说明](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/)。

#### 4.6.1 模型与 DDL

- [ ] 三库位于同一应用、同一环境的 RDS 主实例，库归属、普通访问与受控事务权限清楚。
- [ ] 七张表的行粒度与 4.1 一致；会员记录是当前状态，变更记录是逐次历史，关注与点赞是当前关系。
- [ ] 每张表都有独立的正数雪花 `BIGINT` 主键，不存在 `AUTO_INCREMENT`、无符号整数、物理外键或 `CHECK`；业务规则未转移到触发器或存储过程。
- [ ] 三库与七表均显式声明 `utf8mb4`、`utf8mb4_0900_bin`，每张表都使用 InnoDB，字符列按规则继承。
- [ ] 字段名、索引名和注释准确说明角色、范围、单位及 UTC 语义；字段容量与接口契约一致。
- [ ] 时间列统一 `DATETIME(3)`，没有 `TIMESTAMP` 类型；所有实际连接及应用写入均按基线使用 UTC。
- [ ] 必填字段没有虚假默认值；未支付时间、未知流水、未提供头像及首购前值使用有说明的 SQL `NULL`。
- [ ] 外部账户身份、当前权益、关注、点赞、订单与成功流水的唯一性范围正确，创建和解除流程不会绕过这些约束。
- [ ] 只有帖子使用软删除；当前关注、当前点赞不设置删除标记；订单与权益历史不因帖子或用户停用而清理。
- [ ] Go 映射符合 2.6，内部雪花 ID 为 `int64`，外部账户原始标识为 `string`；可空列使用规定的 `sql.Null*`，GORM 主键声明 `autoIncrement:false`。
- [ ] 新增公共业务词已按 1.5 记录含义，模型与受控 SQL 迁移一致，生产启动不执行 `AutoMigrate`。

#### 4.6.2 业务与并发

| 检查场景 | 预期结果 |
| --- | --- |
| 同一外部账户用不同请求并发注册 | 最多创建一个用户，返回同一用户身份；不覆盖原资料、不自动启用已停用账户 |
| 并发关注、重复关注与自关注 | 相同有向关系最多一条，反向关注不受影响；自关注被应用拒绝 |
| 取消后再次关注或点赞 | 当前关系物理删除，新的主动操作生成新关系 ID；旧请求重放只返回原回执，不重建关系 |
| 两个用户同时互相关注 | 两个入口按相同用户 ID 顺序加锁，避免因相反加锁顺序制造死锁 |
| 并发点赞、取消与计数 | 每次实际关系变化只调整一次计数；重复请求不调整，正常完成后计数与关系一致 |
| 删帖与点赞同时发生 | 通过同一帖子锁串行处理；删除后新互动失败，不留下绕过状态检查的新关系 |
| 删除、恢复帖子 | 删除时保留原关系和计数；恢复只恢复仍存在的关系，已取消点赞不复活 |
| 删除、恢复后的旧请求重放 | 原请求只返回原回执；旧删除不再次删除已恢复帖子，旧恢复不重新恢复后来再次删除的帖子 |
| 计数重建期间发生互动 | 修复遵守同一帖子锁，不以旧统计结果覆盖并发变化 |
| 两笔订单并发首购或续费 | 先锁用户再处理会员，每用户最多一行，每笔成功订单只增加一次快照时长 |
| 首购、未到期续费、过期续费 | 当前权益、前后历史及时间边界分别符合 4.3.5；固定 30 天不按自然月计算 |
| 同单重复回调、续费后的旧回调 | 核对原流水和历史后返回既有结果，不再次延长，也不要求当前到期时间等于旧历史 |
| 渠道已支付但回调未到达 | 支付核对任务查到成功后复用同一确认模块，补齐订单、权益和历史；与回调并发也只发放一次 |
| 同一渠道流水用于不同订单 | 数据库唯一键拒绝第二次确认，会员和历史写入一起回滚 |
| 回调金额、币种、商户或订单身份不符 | 不修改订单与权益，按渠道核验结果处理异常 |
| 当前权益、历史或订单更新任一步失败 | 整个本地事务回滚，不提交部分业务结果 |
| 提交结果未知、死锁或锁超时 | 核对原请求或订单结果，再按完整事务规则处理，不盲目补发权益或更换 ID |
| 用户停用后收到成功支付回调 | 按原订单履约并保留历史，不重新启用用户，不暂停会员期限 |

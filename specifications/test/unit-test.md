# 单元测试规范

## 1. 目的与适用范围

单元测试验证一个 Go 函数、方法或小型组件的行为。测试在进程内构造输入、初始状态和预期结果，直接调用被测入口。默认单测只需要 Go 工具链和项目依赖，测试数据及运行状态由用例自行准备。

| 测试目标 | 单测写法 |
| --- | --- |
| 纯函数或领域规则 | 直接传入输入，断言返回值和错误，例如昵称长度校验 |
| 内存中的状态变更 | 为每条用例创建对象，调用方法后断言状态及约定的副作用 |
| 小型适配组件 | 在进程内构造适配所需的输入和输出对象，例如用 `httptest.NewRecorder` 检查响应组件写入的状态码和 JSON |

需要启动应用、监听端口，或访问真实数据库、中间件及远端服务的用例，使用独立的集成测试或业务流程测试入口。现有[响应组件单测](../../internal/response/response_test.go)直接构造 Gin Context 和响应记录器，验证响应组件的输出。

## 2. 文件与命名

1. 单测放在被测包的源码目录内，文件名以 `_test.go` 结尾。用一个测试文件组织相关行为。主要对应某个源码文件时，使用相同的文件名主体，例如 `user_profile_validation.go` 对应 `user_profile_validation_test.go`。
2. 通过导出入口验证包的行为时，优先使用 `<package>_test` 并显式导入被测包。确需直接访问未导出的函数、方法、类型或字段，或者直接测试 `package main` 时，使用与源码相同的包名。生产代码的可见性由实际调用需要决定。
3. 测试函数使用 `TestXxx(t *testing.T)`，名称包含被测行为，例如 `TestValidateUserName`。对应同一个源码文件的测试函数，按被测函数或方法在源码中的声明顺序排列。
4. 同一行为有多组输入时，优先用表驱动测试和 `t.Run`。用例结构体放在首次使用它的位置之前。子用例名说明输入场景或预期行为，便于从失败输出定位。
5. 使用标准库 `testing` 编写单测。同类测试共用断言辅助函数，共享的准备步骤也可提取为小型辅助函数。辅助函数集中放在文件末尾，断言辅助函数调用 `t.Helper()`。每条用例的关键输入和预期值应在用例中清楚可见。

使用 GoLand 浏览源码时，可以启用 **File Nesting**。在 macOS 上按 `⌘⇧A` 搜索 `File Nesting`，勾选 **Show files with the same names as nested**，在父后缀 `.go` 对应的子后缀中追加 `_test.go`。同目录下文件名主体相同的源码和测试会在项目树中折叠显示。 [GoLand 文件嵌套说明](https://www.jetbrains.com/help/go/file-nesting-dialog.html)

## 3. 单测覆盖范围

### 3.1 确定需要单测的行为

1. **新增或修改可独立验证的关键行为时，应补对应单测。** 重点覆盖业务规则、权限判断、默认值、数据转换、协议约定、状态变化和错误处理。按方法承担的行为选用例。同一个文件可以同时包含适合单测的纯逻辑和需要集成测试的外部依赖交互。
2. **修复可在单测中复现的缺陷时，应保留最小回归用例。** 用例应能在修复前复现问题，并在修复后验证预期结果。
3. **优先选择能观察预期行为的入口。** 纯声明、直接赋值的构造器、固定转发，以及调用入口已经覆盖的私有辅助方法，可以随调用入口验证。封装引入了独立的默认值、校验、转换或错误映射时，应验证这些行为。私有方法有独立规则且难以从调用入口构造场景时，可在同包直接测试。

### 3.2 按代码类型确定场景与断言

| 代码类型 | 应写单测的行为及断言 | 可由调用入口覆盖 | 交给集成测试的行为 |
| --- | --- | --- | --- |
| 公共工具、领域规则和内存算法 | 对格式、长度、计算、排序或状态变化等规则，覆盖典型输入、有效边界、相邻越界值和具有不同预期的失败场景。断言返回值、错误类别及约定的状态变化。时间相关算法使用固定时钟，例如验证同毫秒发号和时钟回拨。 [雪花发号器](../../internal/snowflake/snowflake.go) | 已由规则入口覆盖的内部计算和参数整理。 | 依赖跨进程协调或共享存储的结果，例如多实例启动后使用各自机器号发号。 |
| DTO、模型与值转换 | 对具有协议含义的编码、解码或转换，断言约定的字段名、值类型、有无、精度和空值语义。例如用户 ID 输出为 JSON 字符串，头像 `nil` 与空字符串分别输出 `null` 和 `""`。 [用户资料 DTO](../../app/domains/user/dto/v1/user_profile/user_profile.go) | 仅承载字段的类型和直接赋值的构造器，可由使用它们的用例覆盖。 | ORM 和驱动对真实数据库列的映射，以及写入后读取的空值、精度和时区行为。 |
| 请求绑定与 Validator | 按本入口的约定选择字段缺失、`null`、显式零值、非法类型、默认值和字段组合等场景。成功时断言交给下一层的参数，失败时断言约定的错误码和字段路径。 [更新资料校验](../../app/domains/user/validator/v1/user_profile/update_user_profile_validator.go) | 原样转发绑定结果可随调用入口验证。复用规则的完整边界由所属包覆盖，本入口验证规则接入和结果映射。 | 实际路由接收请求时的入参绑定、响应状态与错误结构。 |
| 认证、授权、中间件、Controller 与响应组件 | 覆盖允许、拒绝、身份传递和错误映射。可用进程内请求和响应记录器断言状态码、错误码、必要响应头及下一步是否执行。可选认证中间件应验证缺少凭证时匿名继续、已提供无效凭证时拒绝，以及有效身份传递。具体接口是否允许匿名、允许谁访问哪个对象，由该接口的授权用例验证。 [认证中间件](../../app/http/middleware/authentication.go) | 原样透传参数或直接调用公共响应方法，可由 Controller 或接口调用用例覆盖。 | 完整路由中的认证与授权组合。使用外部身份服务时，验证实际对接行为。 |
| Service | 覆盖用例自身的输入约束、可独立构造的业务决策、状态变化和依赖失败分支。断言结果、错误类别和约定的副作用，例如拒绝后状态是否保持、后续写入是否执行。可复用已有的内存替身控制依赖结果。 | 只做固定转发的方法，以及经 Service 入口能稳定触发的私有辅助方法。 | 依赖真实业务数据的读写、实际事务内的状态检查，以及多个组件协作后的持久化结果。 |
| Repository 与外部客户端 | 对可隔离的筛选参数转换、请求构造、响应解码和错误分类写单测，断言实际产生的参数、映射结果和约定错误。 | 无额外规则的查询或 SDK 调用封装，由使用它的入口验证。 | 在真实数据库验证 SQL 的筛选、排序、分页、受影响行数、约束、锁和事务回滚。与外部服务的协议兼容和连通性在相应的测试环境验证。 |
| 配置与启动装配 | 对配置解码、默认值、覆盖优先级和校验写单测。用内存中的配置文本或受控环境变量覆盖有效值、缺失、未知字段和非法值，断言解析结果或错误类别。 [MySQL 配置解析](../../internal/database/mysql/config.go) | 固定配置传递、简单实例装配和路由注册，可以由使用入口验证。 | 完整应用启动、真实配置文件挂载、依赖连通性、启动顺序和退出清理。 |

### 3.3 跨层规则的覆盖归属

同一规则的完整边界用例由规则所属层维护。调用方验证自身增加的输入转换、规则组合、错误映射和访问限制。校验归属与项目的[接口与业务校验规范](../application/api-service-validator.md)一致。

以更新用户资料为例，`models` 单测覆盖昵称的长度、空白和编码边界。Validator 选一个非法昵称确认错误定位到 `user_name`，并验证 `expected_version` 缺失或为 `null` 时拒绝，显式传 `0` 时通过版本字段校验。Service 的纯参数检查验证业务允许的版本范围。MySQL 集成测试预置与请求不同的资料版本，断言 HTTP `409`、业务码 `USER_PROFILE_VERSION_CONFLICT`，并检查数据库中的原资料保持不变。 [昵称校验](../../app/domains/user/models/user_profile_validation.go) · [资料更新](../../app/domains/user/service/user_profile_service.go)

### 3.4 领域模型单测

按实体或领域值对象定位被测行为，沿用第 2 节的同目录、同名测试文件和用例组织约定。优先在 `models_test` 中通过公开入口验证。私有辅助函数随入口覆盖，确有独立规则且难以通过公开入口触发时使用同包测试。[领域文件组织](../application/api-service-validator.md#51-领域规则的归属与组织方式)

| 被测行为 | 场景与断言 |
| --- | --- |
| 字段规则及实体校验 | 覆盖典型合法值、有效边界、紧邻越界值和有不同拒绝原因的输入。长度等边界由测试按业务契约独立表达，例如昵称测试直接构造 64 和 65 个 Unicode 码点。成功时断言校验通过，失败时用 `errors.Is` 断言错误类别。调用方需要区分具体规则时，用 `errors.As` 取得 `*check.Violation` 并核对 `Rule`。 |
| 构造函数及领域操作 | 有默认值、计算、字段关系或状态约束时，为每条用例准备独立对象。成功时核对返回值及相关字段，失败时同时断言错误和实体状态保持原值。一次修改多个字段时，可选其中一个输入无效，验证整次修改被拒绝。 |
| 依赖时间或策略的规则 | 显式传入固定时间或只读策略，覆盖影响结果的临界时刻和允许、拒绝场景。例如会员到期判断分别验证到期前、恰好到期和到期后。 |
| 纯字段声明、枚举及直接赋值 | 由使用这些声明或构造结果的用例覆盖。 |

以头像为例，`models` 测已提供地址的长度和 HTTP(S) 格式，Validator 测创建时能否省略、更新时是否必填，以及错误是否定位到 `avatar_url`。Service 单测验证基于查询结果做出的业务决策，例如重复键后是否能确认账户冲突。实际唯一约束、事务和锁的效果由 MySQL 集成测试验证。[头像地址规则](../../app/domains/user/models/user_profile_validation.go) · [创建用户校验](../../app/domains/user/validator/v1/user_profile/create_user_validator.go) · [更新资料校验](../../app/domains/user/validator/v1/user_profile/update_user_profile_validator.go) · [账户冲突处理](../../app/domains/user/service/user_profile_service.go)

完成后逐函数查看语句覆盖率，结合用例核对规则、错误和状态变化的覆盖。

## 4. 用例设计与断言

1. **让每条用例的目标明确。** 按准备初始状态、执行被测行为、核对结果组织。行为一致的输入选取代表值，能改变结果的输入条件分别建立用例。在每条用例定义前写注释，说明为什么选择这个输入，以及期望验证的具体行为。
2. **显式写出预期。** 预期来自接口、领域规则或回归要求。例如昵称规则允许最多 64 个 Unicode 码点，直接构造 64 和 65 个码点的输入。边界由测试独立表达，以便业务上限意外变化时用例能失败。
3. **断言调用方依赖的结果。** 检查返回值、错误及可观察的状态变化。对失败后应保留原状态的操作，同时检查原状态。错误分类使用 `errors.Is`，结构化错误使用 `errors.As` 后检查约定字段。错误文案属于行为约定时，才比较具体文本。
4. **让失败信息可定位。** 输出实际值和预期值。前置条件失败、后续断言无法继续时，用 `t.Fatal` 或 `t.Fatalf`。可以独立核对的多个结果可用 `t.Error` 或 `t.Errorf` 一次报告。

## 5. 依赖与可重复执行

1. **每条用例独立准备状态。** 用字面量、构造函数或小型数据构造函数准备输入。对会被修改的切片、映射和对象，为每条用例创建自己的实例，使其能单独运行或换序运行。
2. **在内存里控制依赖。** 现有代码允许传入依赖时，可以用固定时钟、固定随机源或简单的内存替身来控制结果。测试只断言当前单元的行为。需要验证真实依赖交互时，使用集成测试。
3. **显式控制进程状态。** 测试环境变量读取时，用 `t.Setenv` 设置并恢复测试值。确需修改其他进程级状态时，立即登记 `t.Cleanup` 恢复。只有用例及其父级都与共享可变状态隔离时，才使用 `t.Parallel`。
4. **使时间和执行顺序可控。** 日期相关用例传入固定时间，并明确时区。并发行为通过可观测的同步信号断言，等待应有明确上限。

- 整数检查单测展示多个测试函数按源码顺序排列，同类用例共用断言辅助函数。[整数检查单测](../../internal/check/scalar/integer_test.go)

## 7. 执行与维护

从项目根目录使用满足 [go.mod](../../go.mod) 版本要求的 Go 工具链执行。

| 目的 | 命令 |
| --- | --- |
| 运行全部单测 | `go test ./...` |
| 运行用户领域 `models` 包的单测 | `go test ./app/domains/user/models` |
| 运行某个测试函数 | `go test ./app/domains/user/models -run '^TestValidateUserName$' -v` |
| 跳过测试结果缓存并重新执行 | `go test -count=1 ./...` |
| 生成各被测包的覆盖率报告 | `go test -coverprofile=coverage.out ./...` |
| 查看报告中的函数覆盖率 | `go tool cover -func=coverage.out` |

按目录运行时，选择被测包所在的目录。提交时，测试随对应行为的变更一起维护。覆盖率用于定位遗漏的代码，评审时检查新增或变更的行为是否有清晰、可独立重跑的用例。

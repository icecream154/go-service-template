# 单元测试规范

## 1. 目的与适用范围

**纯逻辑以单元测试为主，单接口完整链路由集成测试验证，多个接口组合的产品用例由业务测试验证，不为了单测改变 Service 的正常结构。** Service 和 Controller 中，完全没有外部依赖且包含实际业务逻辑的函数或方法必须编写单元测试；依赖数据库、Client 或应用运行环境的完整流程按测试目标交给[集成测试](integration-test.md)或[业务测试](business-test.md)。不能按所在层一概免除单测，具体分工见第 3.6 节。

单元测试验证一个 Go 函数、方法或小型组件的行为。测试在进程内构造输入、初始状态和预期结果，直接调用被测入口。默认单测只需要 Go 工具链和项目依赖，测试数据及运行状态由用例自行准备。

| 测试目标 | 单测写法 |
| --- | --- |
| 纯函数或领域规则 | 直接传入输入，断言返回值和错误，例如昵称长度校验 |
| 内存中的状态变更 | 为每条用例创建对象，调用方法后断言状态及约定的副作用 |
| 小型适配组件 | 在进程内构造适配所需的输入和输出对象，例如用 `httptest.NewRecorder` 检查响应组件写入的状态码和 JSON |

需要启动应用、监听端口，或访问真实数据库、中间件及远端服务的用例，使用独立的集成测试或业务测试入口。现有[响应组件单测](../../internal/response/response_test.go)直接构造 Gin Context 和响应记录器，验证响应组件的输出。

## 2. 文件与命名

1. 单测放在被测包的源码目录内，文件名以 `_test.go` 结尾。用一个测试文件组织相关行为。主要对应某个源码文件时，使用相同的文件名主体，例如 `user_profile_validation.go` 对应 `user_profile_validation_test.go`。
2. 通过导出入口验证包的行为时，优先使用 `<package>_test` 并显式导入被测包。确需直接访问未导出的函数、方法、类型或字段，或者直接测试 `package main` 时，使用与源码相同的包名。生产代码的可见性由实际调用需要决定。
3. 测试函数使用 `TestXxx(t *testing.T)`，名称包含被测行为，例如 `TestValidateUserName`。**测试代码必须与被测源码保持相同顺序。** 对应同一个源码文件的测试函数，严格按被测函数或方法的声明顺序排列；同一方法的多个测试连续放置。跳过不需要单测的方法时，不改变其他测试的相对顺序。测试辅助函数集中放在文件末尾。
4. 同一行为有多组输入时，优先用表驱动测试和 `t.Run`。用例结构体放在首次使用它的位置之前。子用例名说明输入场景或预期行为，便于从失败输出定位。**每条表驱动用例和每个独立场景前必须有注释**，说明构造该输入的目的和预期验证的行为，不能只用测试名称或整组测试的总注释代替。
5. 使用标准库 `testing` 编写单测。同类测试共用断言辅助函数，共享的准备步骤也可提取为小型辅助函数。辅助函数集中放在文件末尾，断言辅助函数调用 `t.Helper()`。每条用例的关键输入和预期值应在用例中清楚可见。

使用 GoLand 浏览源码时，可以启用 **File Nesting**。在 macOS 上按 `⌘⇧A` 搜索 `File Nesting`，勾选 **Show files with the same names as nested**，在父后缀 `.go` 对应的子后缀中追加 `_test.go`。同目录下文件名主体相同的源码和测试会在项目树中折叠显示。 [GoLand 文件嵌套说明](https://www.jetbrains.com/help/go/file-nesting-dialog.html)

## 3. 单测覆盖范围

### 3.1 确定需要单测的行为

1. **新增或修改纯逻辑、领域规则和公共组件的关键行为时，必须补对应单测。** 重点覆盖规则边界、默认值、数据转换、协议约定、内存状态变化和错误处理。Service 与 Controller 中已有的无外部依赖业务方法同样必须覆盖；涉及真实依赖的业务编排和状态变更按目标由集成测试或业务测试验证。领域规则按既有分层放在 models 中，不为单测额外拆分业务执行链路。
2. **修复可在单测中复现的缺陷时，应保留最小回归用例。** 用例应能在修复前复现问题，并在修复后验证预期结果。
3. **在单测覆盖范围内，优先选择能观察预期行为的入口。** 纯声明、直接赋值的构造器、固定转发，以及调用入口已经覆盖的私有辅助方法，可以随调用入口验证。封装引入了独立的默认值、校验、转换或错误映射时，应验证这些行为。私有方法有独立规则且难以从调用入口构造场景时，可在同包直接测试。
4. **DTO 按是否实现数据处理或转换逻辑确定单测要求。** 纯结构体声明的 DTO 不需要且不允许编写单测；DTO 自身实现的数据处理或数据转换函数、方法必须编写单测。具体边界见第 3.7 节。

### 3.2 按代码类型确定场景与断言

| 代码类型 | 应写单测的行为及断言 | 可由调用入口覆盖 | 交给集成测试、业务测试或专项验证的行为 |
| --- | --- | --- | --- |
| 公共工具、领域规则和内存算法 | 对格式、长度、计算、排序或状态变化等规则，覆盖典型输入、有效边界、相邻越界值和具有不同预期的失败场景。断言返回值、错误类别及约定的状态变化。时间相关算法使用固定时钟，例如验证同毫秒发号和时钟回拨。 [雪花发号器](../../internal/snowflake/snowflake.go) | 已由规则入口覆盖的内部计算和参数整理。 | 依赖跨进程协调或共享存储的结果，例如多实例启动后使用各自机器号发号。 |
| DTO | DTO 自身实现的数据处理或数据转换函数、方法必须单测，验证处理结果、边界、空值和错误行为。纯结构体声明不需要且不允许编写单测，字段标签和类型别名也属于声明。 [DTO 单测边界](#37-dto-单测) | 请求绑定、Controller 转换和响应输出按实际执行逻辑在所属层验证，不为纯声明另设单测。 | 实际接口的请求、响应字段及序列化协议兼容性。 |
| 模型与值转换 | 对自行实现的编码、解码或转换，断言结果的类型、精度、空值语义及错误。例如 SQL NULL 与有效空值之间的转换。 [数据库值转换](../../internal/database/sqlvalue/string.go) | 仅承载字段的模型类型和直接赋值的构造器，可由使用它们的用例覆盖。 | ORM 和驱动对真实数据库列的映射，以及写入后读取的空值、精度和时区行为。 |
| 请求绑定与 Validator | 按本入口的约定选择字段缺失、`null`、显式零值、非法类型、默认值和字段组合等场景。成功时断言交给下一层的参数，失败时断言约定的错误码和字段路径。 [更新资料校验](../../app/domains/user/validator/v1/user_profile/update_user_profile_validator.go) | 原样转发绑定结果可随调用入口验证。复用规则的完整边界由所属包覆盖，本入口验证规则接入和结果映射。 | 实际路由接收请求时的入参绑定、响应状态与错误结构。 |
| 认证、授权、中间件与响应组件 | 覆盖组件自身的允许、拒绝、身份传递和协议输出。可用进程内请求和响应记录器断言状态码、错误码、必要响应头及下一步是否执行。可选认证中间件验证缺少凭证时匿名继续、已提供无效凭证时拒绝，以及有效身份传递。 [认证中间件](../../app/http/middleware/authentication.go) | 原样透传参数或直接调用公共响应方法，由组件入口覆盖。 | 完整路由中的认证、接口访问范围与对象权限组合；使用外部身份服务时验证实际对接行为。 |
| Service 与 Controller | 对完全无外部依赖且有实际业务逻辑的方法必须写单测，包括参数规则组合、纯权限判断、结果整理、空值与时间转换、错误码和响应映射。直接调用现有方法，不 mock Repository、Client 或 Service。 | 无逻辑的构造器、单纯字段声明或固定转发可随使用入口覆盖；被复用的领域规则完整边界由 models 包覆盖。 | 使用真实路由、认证、Service 和数据依赖，验证完整的输入、对象权限、业务决策、错误映射、事务、持久化与内部服务协作。 [测试分工](#36-service-与-controller-的测试分工) |
| Repository 与外部客户端 | 对可隔离的筛选参数转换、请求构造、响应解码和错误分类写单测，断言实际产生的参数、映射结果和约定错误。 | 无额外规则的查询或 SDK 调用封装，由使用它的入口验证。 | 在真实数据库验证 SQL 的筛选、排序、分页、受影响行数、约束、锁和事务回滚。与外部服务的协议兼容和连通性在相应的测试环境验证。 |
| 配置与启动装配 | 对配置解码、默认值、覆盖优先级和校验写单测。用内存中的配置文本或受控环境变量覆盖有效值、缺失、未知字段和非法值，断言解析结果或错误类别。 [MySQL 配置解析](../../internal/database/mysql/config.go) | 固定配置传递、简单实例装配和路由注册，可以由使用入口验证。 | 完整应用启动、真实配置文件挂载、依赖连通性、启动顺序和退出清理。 |

### 3.3 跨层规则的覆盖归属

同一规则的完整边界用例由规则所属层维护。调用方验证自身增加的输入转换、规则组合、错误映射和访问限制。校验归属与项目的[接口与业务校验规范](../application/api-service-validator.md)一致。

以更新用户资料为例，`models` 单测覆盖昵称的长度、空白和编码边界。Validator 选一个非法昵称确认错误定位到 `user_name`，并验证 `expected_version` 缺失或为 `null` 时拒绝，显式传 `0` 时通过版本字段校验。Service 的 `validateUpdateUserProfileParams` 没有外部依赖，必须单测验证版本范围、必填头像及规则组合；Controller 的纯错误映射单测验证版本冲突对应的错误码。接口集成测试再预置与请求不同的真实资料版本，断言 HTTP `409`、业务码 `USER_PROFILE_VERSION_CONFLICT`，并检查数据库中的原资料保持不变。 [昵称校验](../../app/domains/user/models/user_profile_validation.go) · [资料更新](../../app/domains/user/service/user_profile_service.go)

### 3.4 领域模型单测

按实体或领域值对象定位被测行为，沿用第 2 节的同目录、同名测试文件和用例组织约定。优先在 `models_test` 中通过公开入口验证。私有辅助函数随入口覆盖，确有独立规则且难以通过公开入口触发时使用同包测试。[领域文件组织](../application/api-service-validator.md#51-领域规则的归属与组织方式)

| 被测行为 | 场景与断言 |
| --- | --- |
| 字段规则及实体校验 | 覆盖典型合法值、有效边界、紧邻越界值和有不同拒绝原因的输入。长度等边界由测试按业务契约独立表达，例如昵称测试直接构造 64 和 65 个 Unicode 码点。成功时断言校验通过，失败时用 `errors.Is` 断言错误类别。调用方需要区分具体规则时，用 `errors.As` 取得 `*check.Violation` 并核对 `Rule`。 |
| 构造函数及领域操作 | 有默认值、计算、字段关系或状态约束时，为每条用例准备独立对象。成功时核对返回值及相关字段，失败时同时断言错误和实体状态保持原值。一次修改多个字段时，可选其中一个输入无效，验证整次修改被拒绝。 |
| 依赖时间或策略的规则 | 显式传入固定时间或只读策略，覆盖影响结果的临界时刻和允许、拒绝场景。例如会员到期判断分别验证到期前、恰好到期和到期后。 |
| 纯字段声明、枚举及直接赋值 | 由使用这些声明或构造结果的用例覆盖。 |

以头像为例，`models` 测已提供地址的长度和 HTTP(S) 格式，Validator 测创建时能否省略、更新时是否必填，以及错误是否定位到 `avatar_url`。账户冲突的业务解释通过集成测试验证：使用真实 MySQL 预置账户并发起重复创建请求，同时检查响应错误与最终记录。唯一约束、事务和锁的效果也在该环境中验证。[头像地址规则](../../app/domains/user/models/user_profile_validation.go) · [创建用户校验](../../app/domains/user/validator/v1/user_profile/create_user_validator.go) · [更新资料校验](../../app/domains/user/validator/v1/user_profile/update_user_profile_validator.go) · [账户冲突处理](../../app/domains/user/service/user_profile_service.go)

完成后逐函数查看语句覆盖率，结合用例核对规则、错误和状态变化的覆盖。

### 3.5 接口 Validator 单测

每个用例的测试与对应的 `<use_case>_validator.go` 同目录，命名为 `<use_case>_validator_test.go`。测试函数顺序、用例注释和共享辅助函数沿用第 2、4 节。需要直接调用 `validateXxxRequest` 时使用与源码相同的包名。 [Validator 的结构与入口顺序](../application/api-service-validator.md#61-validator-的结构与入口顺序)

| 被测行为 | 场景与断言 |
| --- | --- |
| 绑定与默认值 | 用实际 Query 或 JSON 表达接口关心的输入状态，按契约选择缺失、`null`、显式零值和类型不匹配。入口准备默认值时，分别验证省略字段会使用默认值、显式输入会参与后续校验。 |
| 字段及集合规则组合 | 在同包调用私有校验函数，成功时核对 DTO 的字段值和空明细。已知输入问题应返回字段明细和 `nil` 错误。覆盖必填、可选、依赖条件和数量口径等本接口规则，断言字段路径、明细顺序和数量。默认每个字段保留一条明细。集合按契约的数量口径先检查整体，再检查元素，并核对输入保留原顺序和值。公共检查和领域规则的完整边界由所属包验证。 |
| 绑定失败的 HTTP 响应 | 构造语法错误或类型不匹配的请求，直接调用 Validator 入口，断言 HTTP `400`、`INVALID_ARGUMENT`、非空消息，且响应省略 `error.details`。 |
| 字段校验失败的 HTTP 响应 | 构造可绑定但违反字段规则的请求，断言 HTTP `400`、`INVALID_ARGUMENT`，并核对 `error.details` 的字段、顺序和原因。`error.message` 使用首条 `FieldError.Error()`。 |

HTTP 入口测试用 Gin Context 和 `httptest.NewRecorder` 在进程内执行。失败时核对 JSON 响应头，断言响应体中的 `data` 为 `null`，并用 `ctx.IsAborted()` 验证处理链中止。成功绑定及校验可通过独立校验入口检查 DTO；交给 Controller 后的流程由接口集成测试覆盖，同时验证实际路由与中间件的协作。不为 Validator 单测替换 Controller 或初始化真实业务依赖。 [私有校验规则](../application/api-service-validator.md#62-私有校验函数的规则组合) · [集合与错误汇总](../application/api-service-validator.md#63-集合字段依赖与错误汇总) · [错误输出与终止](../application/api-service-validator.md#92-输出与终止)

通过现有依赖或策略可构造内部规则故障时，验证私有校验函数返回原错误并丢弃已收集的字段明细，同时核对入口返回 HTTP `500` 和 `INTERNAL_ERROR`。完成后逐函数检查语句覆盖率，说明固定有效规则下的防御性错误分支和 Controller 转交的验证归属。

### 3.6 Service 与 Controller 的测试分工

**根据方法自身的依赖和职责选择测试方式，不能仅因属于 Service 或 Controller 就省略单测。** 无外部依赖的业务逻辑必须单测；涉及真实依赖的单接口链路由集成测试验证，多接口产品用例由业务测试验证。Service 直接调用项目已初始化的 Repository、Client 和其他 Service，正常组织事务；不为测试强制内外分离、构造函数注入、逐方法函数注入，或增加模拟事务的回调结构。私有辅助函数仅按业务职责和复用需要提取。[Service 执行结构](../application/api-service-validator.md#service-执行结构)

#### 必须单测的方法

1. **无外部依赖按完整方法及其实际调用链判断。** 方法不访问数据库、文件、网络或外部服务，不调用 Repository、Client，也不依赖需要初始化的 Runtime、共享日志或追踪等运行环境。标准库计算、确定性的 `models`、`check`、值转换函数，以及调用方提供的内存对象不属于这类外部依赖。不能只挑有依赖方法中恰好提前返回的分支，就将整个方法视为无依赖方法。
2. **包含业务判断或协议语义就必须覆盖。** 参数校验与规则组合、基于输入的权限判断、状态和分页结果整理、SQL NULL 与时间转换、错误分类及响应映射都属于实际逻辑；公开方法和私有辅助函数采用相同标准。无状态对象的空构造器、纯声明和无规则的固定转发无需单独测试。
3. **直接执行现有实现。** 同包调用私有方法，通过输入值和返回值验证规则；对只依赖内存 HTTP 对象的响应方法，可以使用 Gin Context 和 `httptest.NewRecorder`，检查状态码、响应头、JSON 和处理链终止，不启动应用或监听端口。不初始化全局依赖，也不新增函数注入、接口或 mock 来绕过外部依赖。
4. **用例解释目标并遵守源码顺序。** 按第 2、4 节，在每条用例前注释输入选择及预期行为，测试函数严格对应源码声明顺序。覆盖该方法自身的成功、边界、拒绝和输入保持不变等约定；复用规则选代表用例验证接入，完整边界仍由规则所属包维护。

| 现有无外部依赖逻辑 | 单测重点 |
| --- | --- |
| Service Params 校验 | 正数标识、分页和批量数量、偏移溢出、版本范围、必填与可选字段、本人关系及游标绑定。 |
| 会员查询结果和历史分页整理 | 未开通、有效和过期状态的组合，异常数据分类，裁剪探测行，使用实际返回末条记录生成下一页令牌。 |
| 表模型和 DTO 转换 | SQL NULL 与有效空值的区别、非 nil 空集合、顺序、UTC 时间以及需要复制的可变值。 |
| Controller 错误与响应映射 | 通用码和业务码、错误链分类、认证挑战头、原错误消息、空数据和终止响应。 |

#### 与集成测试、业务测试的衔接

1. **单接口完整链路遵守[集成测试规范与方案](integration-test.md)。** 从真实 HTTP 入口执行认证、绑定、业务和数据访问，使用隔离的真实数据库及正式 DDL。没有 HTTP 入口的公开 Service 可在同一真实依赖环境中补充验证，但不能计入 HTTP 接口覆盖。
2. **多接口产品用例遵守[业务测试规范与方案](business-test.md)。** 使用前序接口实际返回的身份、标识、版本和结果推进流程，不能直接写库代替关键中间步骤。不同流程独立准备前置状态。
3. **公司服务保留真实 Client，第三方 SDK 整体 Mock。** 公司服务连接受控协议模拟服务，核对真实请求和响应处理；第三方 SDK 在依赖装配边界整体替换，不执行真实 SDK，不要求使用 HTTP 或暴露访问地址，核对调用方法、参数、次数及结果处理。该替换属于集成测试和业务测试的环境装配，不改变无外部依赖方法的单测范围，也不要求为 Service 增加逐方法 Mock。真实 SDK 和供应商联调另行明确范围，不能把模拟依赖通过视为真实联调通过。
4. **响应、状态及副作用共同断言。** 按提交边界验证持久化、回滚、锁、唯一约束、并发冲突及不应发生的调用。HTTP 失败或超时不统一表示没有写入；等内部工作结束后再清理数据。具体用例和生命周期要求集中维护在集成测试规范中。
5. **执行入口彼此独立。** 集成测试使用 `integration` 构建标签，业务测试使用 `business` 构建标签，默认 `go test ./...` 只运行单测。两类测试共用环境设施，但分别执行和报告；当前已提供 MySQL 环境设施及独立验收，HTTP 接口与业务用例仍待实现，单测通过不能代替其验证结果。

### 3.7 DTO 单测

1. **纯结构体声明的 DTO 不需要且不允许编写单测。** 只有字段、字段标签、结构体嵌套或类型别名，没有自身数据处理或数据转换实现的 DTO，均属于纯声明。不能仅因包含 `json:",string"`、指针或切片字段，就为它创建序列化测试；仅构造 DTO 并调用标准库编码、解码来检查字段声明或标签的用例应删除。
2. **DTO 自身实现的数据处理或数据转换函数、方法必须编写单测。** 直接调用实际实现，按行为覆盖正常输入、有效边界、空值和失败场景，断言返回结果、错误及约定的状态变化。测试与实现同目录，沿用第 2、4 节的文件命名、源码顺序和用例注释要求。
3. **按逻辑所在位置维护测试。** Controller 或 Service 中的 DTO 转换函数仍按第 3.6 节测试；请求绑定和校验按第 3.5 节测试。调用方使用纯结构体 DTO，不影响调用方自身逻辑的单测要求。协议字段可随实际绑定、转换或响应入口验证，不为纯声明另设单测，也不把纯声明测试移到其他包中继续保留。
4. **只为已有实现补测。** 不为保留或新增单测而给 DTO 添加处理方法、迁移其他层逻辑，或增加无实际用途的包装函数。例如当前的 `UserProfile`、`UserMembership` 和 `MembershipChangeRecord` 仅声明字段，不创建对应 DTO 单测文件；后续新增实际处理或转换实现时，同步补充该实现的单测。

## 4. 用例设计与断言

1. **必须用注释解释每条用例的目标。** 按准备初始状态、执行被测行为、核对结果组织。行为一致的输入选取代表值，能改变结果的输入条件分别建立用例。在每条表驱动条目或独立场景前写注释，说明为什么选择这个输入，以及期望验证的具体行为。例如“用恰好 100 个 ID 验证批量上限允许通过，且重复项仍计入提交数量”。测试名称、重复代码含义的注释或整组测试的说明不能代替单条用例的目标说明。
2. **显式写出预期。** 预期来自接口、领域规则或回归要求。例如昵称规则允许最多 64 个 Unicode 码点，直接构造 64 和 65 个码点的输入。边界由测试独立表达，以便业务上限意外变化时用例能失败。
3. **断言调用方依赖的结果。** 检查返回值、错误及可观察的状态变化。对失败后应保留原状态的操作，同时检查原状态。错误分类使用 `errors.Is`，结构化错误使用 `errors.As` 后检查约定字段。错误文案属于行为约定时，才比较具体文本。
4. **让失败信息可定位。** 输出实际值和预期值。前置条件失败、后续断言无法继续时，用 `t.Fatal` 或 `t.Fatalf`。可以独立核对的多个结果可用 `t.Error` 或 `t.Errorf` 一次报告。

## 5. 依赖与可重复执行

1. **每条用例独立准备状态。** 用字面量、构造函数或小型数据构造函数准备输入。对会被修改的切片、映射和对象，为每条用例创建自己的实例，使其能单独运行或换序运行。
2. **在单测范围内控制输入与依赖。** 纯规则和公共组件可通过现有入口使用固定时钟、固定随机源或简单的内存替身。测试只断言当前单元的行为，不为 Service 或 Controller 增加可替换的业务依赖；真实业务链路与依赖交互按第 3.6 节使用集成测试或业务测试。
3. **显式控制进程状态。** 测试环境变量读取时，用 `t.Setenv` 设置并恢复测试值。确需修改其他进程级状态时，立即登记 `t.Cleanup` 恢复。只有用例及其父级都与共享可变状态隔离时，才使用 `t.Parallel`。
4. **使时间和执行顺序可控。** 日期相关用例传入固定时间，并明确时区。并发行为通过可观测的同步信号断言，等待应有明确上限。

## 7. 执行与维护

从项目根目录使用满足 [go.mod](../../go.mod) 版本要求的 Go 工具链执行。

| 目的 | 命令 |
| --- | --- |
| 运行全部单测 | `go test ./...` |
| 运行用户领域 `models` 包的单测 | `go test ./app/domains/user/models` |
| 运行用户资料 Validator 单测 | `go test ./app/domains/user/validator/v1/user_profile` |
| 运行 Service 与 Controller 的无外部依赖逻辑单测 | `go test ./app/domains/user/service ./app/domains/user/controller/v1` |
| 运行某个测试函数 | `go test ./app/domains/user/models -run '^TestValidateUserName$' -v` |
| 跳过测试结果缓存并重新执行 | `go test -count=1 ./...` |
| 生成各被测包的覆盖率报告 | `go test -coverprofile=coverage.out ./...` |
| 查看报告中的函数覆盖率 | `go tool cover -func=coverage.out` |

按目录运行时，选择被测包所在的目录。提交时，测试随对应行为的变更一起维护。覆盖率用于定位单测范围内遗漏的规则，Service 与 Controller 逐个核对无外部依赖业务方法的覆盖，不用包含真实依赖流程的整个文件或包的覆盖率代替该检查，也不为提高覆盖率拆分生产执行链路。评审同时检查每条用例的目标注释和测试函数的源码顺序；DTO 逐项确认纯声明没有专门单测、自身的数据处理和转换实现都有对应单测。业务流程的验证记录应单独说明集成测试环境、执行入口、覆盖场景和未验证项；默认单测通过不能代替集成测试结果。
